## 1. エグゼクティブサマリ

- **作るもの**: 発明の説明（または対象特許）を入力に、キーワード×分類コード（FI／Fターム／IPC）のブール検索式を、検索結果からの逆算と適合度評価により再帰的に改善して作成するシステム。
- **基本コンセプト**: 初回は広めの式で母集団を取り、結果に適合度を付け、適合群と非適合群の分類・語の分布差から次の式を逆算する。この「生成→実行・評価→改良」のループを、改善が止まるか再現率の推定値が目標に達するまで回す。
- **手法の格上げ**: 逆算の統計は RSJ 重み（確率的関連性フィードバック）、改良の探索は目的関数付きの変換探索（決定木・変換操作・LLM提案を同じ評価器で競わせる）、適合文献の発見は継続的能動学習（CAL）、停止判定は無作為標本による再現率推定で行う。
- **2案**: 完全自動版（案A）とセミオート版（案B）。両案は同一の共通コアを持ち、差は各ゲートの「決定者」が自動ポリシーか人かだけ。
- **推奨**: 案Bを先行構築し、人の判断ログを蓄積して案Aへ段階移行する。二重開発にならない設計。
- **成立条件**: 案Aは LLM API と商用DBのAPI（または自前索引）が必須。案Bは社内で許可されたLLM経路と Excel／Python で着手できる。
- **期待効果**: 検索式作成時間の短縮、属人性の低減、全ての語・分類に根拠が付いた監査可能な検索式、再現率の定量的な担保。

## 2. 背景と課題

検索式作成は調査担当の経験に依存している。同義語の展開、分類コードの当たり付け、母集団サイズの調整を試行錯誤で行うため時間がかかり、「なぜその語・その分類を選んだか」が記録に残りにくい。再現率（取り逃し）は感覚的にしか把握できず、調査品質の説明が難しい。

本システムの狙いは、試行錯誤のループそのものを機械化し、人は判断に集中できるようにすること、全ての語・分類に由来文献と統計値の根拠を付けること、再現率を推定値と信頼区間で示すことである。

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| 検索観点（ブロック） | 発明を課題・構成・効果・用途などの軸に分解した単位。ブール式では観点内を OR、観点間を AND で結合する |
| 必須観点／補助観点 | AND 軸として常に用いる観点／狭める時だけ用いる観点。G1 で人が指定し、反復中は固定 |
| 母集団 U | 広め案が DB から返す文献集合。狭い式 Q の結果は U の部分集合として手元データで評価できる |
| 既知文献（シード） | 依頼時点で適合と分かっている文献。正解セットの初期値 |
| 累積適合プール（Pool） | 各反復で適合と判定された文献の累積集合。既知文献を含む。再現率の分母 |
| 適合度 | 文献が調査対象にどれだけ合致するかの採点。観点ごとに 0〜3、総合 0〜3。採点者（人／LLM／分類器）を必ず記録 |
| 適合ラベル | 総合適合度 ≥ 2 を適合とみなす二値ラベル（閾値は初期値（仮）） |
| 3案 | 広め／標準／狭めの3つの検索式バリアント。常にセットで生成する |
| ゲート G1〜G4 | パイプライン中で判断が必要な地点（§8.1） |
| 決定者 | ゲートで判断する主体。人（Human）または自動ポリシー（Policy） |
| DSL | 検索式の内部表現（JSON）。DB 方言に依存しない（§9.2） |
| レンダラ／パーサ | DSL を特定 DB の検索式文字列に変換する部品／その逆（§9.3） |
| RSJ 重み | Robertson–Sparck Jones の関連性重み。適合・非適合の 2×2 表から語・コードの識別力を出す（§10.3） |
| CAL | Continuous Active Learning。分類器で順位付け→上位を判定→再学習を繰り返す高再現率レビュー手法（§10.7） |

## 4. スコープ

**対象調査種別**: 先行技術調査、無効資料調査、侵害予防調査、技術動向調査（定期監視 SDI を含む）。調査種別は設定値として全アルゴリズムの閾値に影響する。

**対象DB**: J-PlatPat（人が実行する経路のみ）、社内契約の商用DB（API または CSV 出力）。海外DB（Espacenet 等）は将来対応とし、DSL とレンダラは方言追加で対応できる構造にする。

**対象国**: 日本を主対象。米欧中は英語キーワードと IPC／CPC による将来対応。

**入力**: 技術説明文（発明提案書、クレーム案、技術メモ）または対象特許番号、調査種別、既知文献（任意）、期間・国などの制約。

**出力**:
1. 3案の検索式（DB 別レンダリング済み文字列と DSL）
2. 検索観点表（観点×語×分類、採否と理由）
3. 根拠レポート（各語・各分類の採用理由、由来文献、RSJ 統計、フリップ率）
4. 評価ログ（反復ごとの件数、既知文献再現率、プール再現率、上位K件適合率、推定再現率）
5. 版履歴（全反復の DSL と判断記録）

**非スコープ**: 公報の全文読解・鑑定、権利範囲の法的判断、J-PlatPat の自動操作、LLM サービス UI の自動操作（本番）、海外DB 対応（Phase 4 以降で再検討）。

## 5. 基本コンセプト

### 5.1 再帰的改善ループ

1. **広めに決める**: 発明を観点に分解し、必須観点だけを AND した広め案で母集団 U を取る。
2. **適合度を付ける**: U の上位 K 件と無作為標本に適合度（0〜3）を付ける。
3. **逆算する**: 適合群と非適合群で FI・Fターム・IPC・語の出現率を比較し（RSJ 重み）、高い群に偏るものを AND 軸・OR 追加の候補、低い群に偏るものを除外・分割の候補にする。
4. **改良する**: 変換候補を目的関数（プール再現率・母集団サイズ・上位K件適合率）で評価し、パレート改善のみ採用する。狭める方向の変換は U の手元データで局所評価でき、DB を叩かずに済む。
5. **止める**: 改善が止まる、または標本による推定再現率が目標に達したら停止し、3案と根拠を出力する。

### 5.2 6段パイプライン

```
[1 入力の構造化] → [2 キーワード展開] → [3 分類付与] → [4 検索式組立]
  （観点は固定）          ↑                                        ↓
                          └──── [6 改良（逆算・変換探索）] ← [5 実行・評価]
```

| 段 | 処理 | 主な部品 |
|---|---|---|
| 1 | 課題・構成・効果・用途に分解し、検索観点（必須／補助）を定義 | LLM（P1）、G1 |
| 2 | 同義語・上位下位概念・表記ゆれ・略語・英訳を展開。由来を記録 | LLM（P2）、同義語辞書、既知文献、簡易トークナイザ |
| 3 | FI／Fターム／IPC 候補を生成し、分類表辞書で照合。既知文献の付与分類を第一候補 | LLM（P3）、分類表辞書、フリップ率 |
| 4 | 観点×語×分類の表から DSL を組み、3案をレンダリング。構文検証 | DSL、レンダラ、パーサ |
| 5 | DB で実行し件数と文献リストを取得。既知文献再現率、プール再現率、上位K件適合率を算出 | DBアダプタ、適合度採点（P4）、評価器 |
| 6 | RSJ 逆算、変換候補生成、局所評価、パレート選択。CAL でプールを拡大。標本で再現率推定 | stats.rsj、learn.boolean、learn.cal、eval.sampling |

### 5.3 決定者の抽象化

各ゲートは `decide(context) -> Decision` の共通インタフェースを持つ。Human 実装は Excel／Jupyter で人が入力し、Policy 実装はルールと閾値で判断する。案Aと案Bの差はこの差し替えだけであり、同一コードベースで両モードを提供する。Human の判断はすべて記録され、Policy のルール作成と LLM プロンプト改善の学習データになる。

### 5.4 設計原則

1. **構文は LLM に書かせない**。LLM は意味側（観点、語、分類候補、採点、変換提案）だけを担い、検索式文字列は DSL からテンプレートで決定的に生成し、パーサで往復検証する。
2. **分類コードは辞書照合**。LLM が出したコードは分類表辞書に存在するものだけを通す。既知文献の付与分類の集計を第一候補にし、複数回生成のフリップ率で確信度を付ける。
3. **評価の主軸は累積プール再現率と母集団サイズ**。第三軸に上位K件適合率。既知文献の再現率は 1.0 を必須条件とする。
4. **常に3案＋根拠**。単一の式を出さない。
5. **観点の骨格は反復中に固定**（クエリドリフト防止）。適合度は「前回結果との類似」ではなく「固定した観点との一致」で採点する。
6. **全ての判断と統計を SQLite に記録**。監査と学習資産のため。
7. **DB アクセスは最小化**。狭める方向の評価は母集団の手元データで局所計算し、広げる時だけ DB を叩く。

## 6. 前提と制約

### 6.1 実行環境

- Windows、Anaconda（Python 3.x）、Jupyter。社内プロキシ（SSL 検査あり）。第三者ソフトのインストール不可、EXE 制限、PyPI アクセス限定。
- **使用可能ライブラリ**: Python 標準ライブラリ＋Anaconda 同梱（numpy、pandas、scikit-learn、openpyxl、matplotlib、ipywidgets、pytest）。pip インストール前提のライブラリは使用しない。必要になった場合は §16 に起票し、承認を待つ。
- **形態素解析器（MeCab 等）は使えない前提**。日本語処理は文字 n-gram と簡易トークナイザ（§10.2）で行う。
- **成果物形式**: 純 Python パッケージ、Excel ブック、SQLite、Markdown／HTML レポート。単一ファイルまたは単一フォルダで配布できる形を優先する。
- **開発環境（Claude Code）と実行環境（社内PC）は別**。開発時も上記の依存制限内に留める。ネットワーク呼び出しは LLM アダプタと DB アダプタに限定し、設定で完全にオフにできる（オフライン fixtures で全機能がテストできる）こと。
- **プロキシ／証明書**: HTTPS_PROXY 等の環境変数と、社内 CA 証明書バンドルのパスを設定で指定できること。

### 6.2 外部サービスの規約（確認済み）

- **J-PlatPat**: 一般の利用を妨げる恐れのある大量ダウンロードや、プログラムによる自動データ収集（ロボットアクセス）は禁止されており、該当行為が見つかると予告なくアクセス制限される（INPIT「利用上のご案内」）。→ 本システムは J-PlatPat を一切自動操作しない。人が実行し、CSV を取り込む経路のみ提供する。
- **特許庁 特許情報取得API**: J-PlatPat 等で提供される出願の経過情報の一部を機械的に取得する試行提供であり、検索機能ではない。新規申込受付は 2024 年 8 月 9 日に終了している。→ 検索実行の基盤には使えない。
- **LLM サービスの UI 自動操作**: 規約・安定性の懸念から本番運用の前提にしない。開発・検証で既存のブラウザ自動化資産を使う場合も、production モードでは無効化する。

### 6.3 機密

- 発明情報を外部 LLM に送る可否は社内ルールに従う。LLM アダプタは「送信前の内容確認（人）」と「送信ログ」を必ず経由する。
- マスキングオプション（社名・人名・具体数値の置換）を持つ。マスキング表は案件ごとに SQLite に保存し、復元は手元で行う。

### 6.4 データ取得

- 逆算・CAL・再現率推定には、母集団 U の各文献について少なくとも **分類コード（FI／Fターム／IPC）と発明の名称**、可能なら **要約・請求の範囲・引用情報** が必要。
- J-PlatPat の CSV 出力に含まれる項目と件数上限、商用DB のエクスポート項目・上限・API 有無は Phase 0 で確認する（§16）。取得できる項目に応じて機能を段階的に有効化する（名称＋分類のみ → RSJ の語は名称由来のみ、CAL は名称＋分類特徴のみ）。

## 7. システム構成案A：完全自動版

### 7.1 構成

```
[調査依頼] ─→ ┌─────────── 自動オーケストレータ（Python／SQLite） ───────────┐ ─→ [成果物]
              │ [生成] ─→ [実行・評価] ─→ [改良] ─┐                          │
              │   ↑                              │  ↻ 停止条件まで反復       │
              │   └──────────────────────────────┘                          │
              └───────────────┬──────────────┬──────────────┬──────────────┘
                              │              │              │
                        [LLM（API）]    [特許DB API／自前索引]   [知識層]
```

| 構成要素 | 役割 |
|---|---|
| オーケストレータ | 6段パイプラインを Policy 決定者で回す。状態と全反復を SQLite にチェックポイント |
| 生成 | P1〜P3 と辞書照合で観点表を作り、DSL を組んで3案をレンダリング |
| 実行・評価 | DB アダプタで実行。件数、既知文献再現率、プール再現率、上位K件適合率（P4） |
| 改良 | RSJ 逆算、変換候補（統計＋LLM 提案）、局所評価、パレート選択。CAL、標本再現率推定 |
| LLM（API 経由） | 構造化出力（JSON スキーマ）、多数決（n サンプル）、フリップ率 |
| 特許DB | 商用DB の API、または特許情報標準データ等から調査分野を絞って作る自前索引（SQLite FTS5、trigram トークナイザ。環境で有効か要確認） |
| 知識層 | 分類表辞書、同義語辞書、調査実績（過去の式と正解文献） |

### 7.2 ループと停止条件

各反復で「変換候補の生成 → 局所評価（U の内側）→ 上位候補のみ DB 実行 → 評価 → パレート更新」を行う。停止条件は以下の論理和（必須条件は常に満たすこと）。

| 種別 | 条件 | 初期値（仮） |
|---|---|---|
| 必須 | 既知文献再現率 = 1.0 | — |
| 必須 | 累積プール再現率 ≥ τ_pool | 0.95 |
| 目標達成 | 母集団サイズが調査種別のレンジ内 | 先行技術 200〜1,500件、無効資料 300〜3,000件、侵害予防 500〜5,000件、技術動向 1,000〜10,000件 |
| 目標達成 | 標本推定再現率の下側信頼限界 ≥ ρ_target（Phase 2 以降） | 0.90 |
| 収束 | パレート改善が T 反復連続で無い | T = 3 |
| 予算 | 反復上限、LLM 呼び出し上限、DB アクセス上限 | 反復 10、LLM 300 回、DB 30 回 |

### 7.3 ガード

- 構文検証（レンダリング後にパーサで往復一致を確認）と辞書照合（実在しないコードは棄却）。
- 確信度の低い分類（フリップ率 > 0.2、初期値（仮））と LLM 提案の語には「要確認」フラグを付け、根拠レポートに明示。
- 退行検知: 新しい式がプールの文献を落としたら、その変換は棄却。
- NOT（除外条件）は既定で無効。有効化する場合も、プールの文献を除外しないことを局所評価で保証。
- ドリフト検知: 観点骨格の不変、初回反復の上位適合文献の保持率（初期値（仮）0.9 未満で警告）。
- 予算上限とアクセス上限（DB の利用規約に従う）。
- 完全自動でも成果物の最終確認は人が行う運用とし、根拠レポートで説明責任を担保する。

### 7.4 成立条件

1. API 経由で呼べる LLM（社内契約）。
2. 商用DB の API、または自前索引（特許情報標準データ等のバルクデータから分野を絞って構築）。
3. 分類表データ（FI／Fターム／IPC の階層とタイトル）。
4. 正解文献の蓄積（過去案件の既知文献・最終適合文献）。

ブラウザ自動化で LLM や DB を代替する案は、UI 変更に脆く規約面の懸念もあるため、本番の前提に置かない。

### 7.5 向く用途

定期監視（SDI）の式メンテナンス、技術動向調査の母集団作成、初版ドラフトの大量生成。

## 8. システム構成案B：セミオート版

### 8.1 4ゲート

```
 システム（提案・整形・記録）            人（判断・実行・承認）
 ┌──────────────────┐                ┌──────────────────┐
 │ 発明の構造化      │ ───────────→ │ G1 観点の確認     │
 └──────────────────┘                └────────┬─────────┘
 ┌──────────────────┐                         ↓
 │ 候補の展開        │ ───────────→ │ G2 候補の採否     │
 └──────────────────┘                └────────┬─────────┘
 ┌──────────────────┐                         ↓
 │ 検索式案の生成    │ ←──┐ ──────→ │ G3 DBで実行       │
 └──────────────────┘    │          └────────┬─────────┘
 ┌──────────────────┐    │                   ↓
 │ 評価と改良提案    │ ───┘ ──────→ │ G4 確定／再反復   │
 └──────────────────┘                └──────────────────┘
```

| ゲート | システムが提示するもの | 人が決めること | 記録する判断 |
|---|---|---|---|
| G1 観点の確認 | P1 による課題・構成・効果・用途の分解と観点案、必須／補助の提案 | 観点の追加・修正・削除、必須／補助の指定。以後固定 | 観点の最終定義、修正理由コード |
| G2 候補の採否 | 語候補（LLM、辞書、既知文献由来、2回目以降は RSJ 統計付き）、分類候補（辞書照合済み、フリップ率、既知文献での出現数） | チェック方式で採用・棄却。語の観点割当の修正 | 各候補の採否と理由コード（RSJ 統計を併記） |
| G3 DB で実行 | 3案の DB 別レンダリング文字列（コピー用） | DB で実行し、件数入力、CSV の取り込み | 件数、CSV パス、実行日時、DB 名 |
| G4 確定／再反復 | 既知文献再現率、プール再現率、上位K件と標本の適合度採点案（P4）、変換候補と局所評価による予測効果、推定再現率 | 採点の確認・修正、変換候補の採否、確定または再反復 | 採点の上書き、採用した変換、確定した3案 |

再反復は G4 → 検索式案の生成へ戻る。G1 の観点は再反復では変更しない（変更が必要なら新しい版として案件を分岐する）。

### 8.2 人の UI

- **Excel 設計シート**（付録B）を判断の主インタフェースにする。シート: 案件、観点、語候補、分類候補、検索式（3案・DB別）、実行結果、判定、ログ。
- **Jupyter ドライバノートブック**がシートの読み書き、LLM 呼び出し、統計計算、レポート生成を担う。ipywidgets による最小限の操作ボタンは任意。
- コマンドライン（`python -m pqb <command>`）でも同じ操作ができること（自動テストと将来の案A化のため）。
- 検索式は「コピーして DB に貼る」前提の文字列として提示し、DB 側の操作はしない。

### 8.3 LLM 経路の3モード

| モード | 動作 | 用途 |
|---|---|---|
| manual | プロンプトをファイル／クリップボードに出力。人が社内許可の LLM 画面に貼り、返答 JSON を貼り戻す。スキーマ検証して取り込む | 現時点の本番既定 |
| api | 設定したエンドポイント（OpenAI 互換／Anthropic／Azure 等）を呼ぶ。プロキシと社内 CA を設定可能 | API が使える場合の本番 |
| browser | 既存のブラウザ自動化資産を使う | 開発・検証のみ。production フラグで無効 |

3モードは同じプロンプトと同じ出力スキーマを使い、上位のコードはモードを意識しない。

### 8.4 学習ループ

- 人の採否・修正はすべて SQLite に記録し、同義語辞書（語、同義語、由来、採用回数）と分類辞書（観点→分類の対応、採用回数）を育てる。
- 判断ログは LLM プロンプトの評価データになる（GEPA 等のプロンプト最適化に接続可能）。人が採用した候補を正例、棄却した候補を負例として、P2／P3 の提案精度を測る。
- G2 の採否ログと G4 の採点ログは、Policy 決定者のルール作成に用いる（案Aへの移行資産）。

### 8.5 向く用途

先行技術調査、無効資料調査、侵害予防調査。再現率の責任を人が負うべき案件。

### 9.2 検索式 DSL

DSL は DB 方言に依存しない JSON。1つの Query は複数の Block（観点）を持ち、Block 内の語は OR、コードは OR、語群とコード群の結合は variant 別のルールで決める。Block 間は AND。

```json
{
  "dsl_version": "1.0",
  "query_id": "CASE-0001/v3/standard",
  "case_id": "CASE-0001",
  "purpose": "prior_art",
  "variant": "standard",
  "blocks": [
    {
      "axis_id": "A",
      "axis_name": "対象物",
      "required": true,
      "terms": [
        {"text": "高強度鋼板", "fields": ["AB", "CL"], "origin": "input", "status": "adopted"},
        {"text": "高張力鋼板", "fields": ["AB", "CL"], "origin": "llm:P2", "status": "adopted"}
      ],
      "codes": [
        {"scheme": "FI", "code": "C22C38/00", "level": "main_group", "origin": "seed:JP2020-000001A", "status": "adopted"}
      ],
      "term_code_join": "OR"
    },
    {
      "axis_id": "B",
      "axis_name": "手段",
      "required": true,
      "terms": [{"text": "焼入れ", "fields": ["AB", "CL"], "origin": "input", "status": "adopted"}],
      "codes": [],
      "term_code_join": "OR"
    }
  ],
  "exclusions": [],
  "date_range": {"from": "2000-01-01", "to": null, "basis": "publication"},
  "countries": ["JP"],
  "provenance": {"iteration": 3, "parent_query_id": "CASE-0001/v2/standard"}
}
```

- `origin` は語・コードの由来（`input`／`seed:<文献番号>`／`llm:P2`／`dict`／`rsj:iter3`／`cal:iter3`／`human`）。根拠レポートに転記する。
- `status` は `candidate`／`adopted`／`rejected`。rejected も DSL に残し、履歴として保持する。
- variant 別の組立ルール（初期値（仮））:

| variant | Block の選択 | Block 内の語群とコード群 |
|---|---|---|
| broad | 必須観点から AND 軸を 1 つ減らす（既定: 分類コードを持つ観点を優先して残す）。フィールドは広い側（TX があれば TX）、コードは一段粗い粒度 | OR |
| standard | 必須観点すべて。フィールドは AB・CL | OR |
| narrow | 必須観点＋補助観点 | 分類が存在する Block では AND（語 AND コード）、それ以外は OR |

- `fields` は抽象フィールド名（`TI` 名称、`AB` 要約、`CL` 請求の範囲、`TX` 全文）。方言ごとの実フィールド名への対応表はレンダラの設定に持つ。

### 9.3 レンダラとパーサ

- 方言は設定ファイル（JSON）で定義する: 演算子（AND／OR／NOT）、括弧、フィールド識別子の書式と位置、分類コードの書式（FI の展開記号・分冊識別記号、Fターム、IPC）、近接演算子の有無と書式、1式の文字数上限、トランケーション記号。
- 初期実装の方言: `jplatpat`（論理式入力）、`generic_boolean`（テスト用）、商用DB は Phase 0 の確認後に追加。
- **J-PlatPat 論理式の正確な文法（フィールド識別子、演算子、分類コードの記法、文字数上限、近接演算子の有無）は公式ヘルプ／操作マニュアルで確認し、テストデータに反映する。本書の例はすべて仮。**
- パーサは人が書いた既存の式を DSL に取り込むために使う（過去案件の後方テスト、few-shot 例の作成）。`parse(render(q)) == q` の往復テストを全方言で必須にする。
- 文字数上限を超える場合は Block 単位で式を分割し、分割式の集合として扱う（結果は和集合）。

### 9.4 LLM アダプタ

- 全プロンプトは JSON スキーマ付きの構造化出力。スキーマ不一致は最大 2 回リトライし、失敗は記録して人に回す。
- `n` サンプル（初期値（仮）: P3・P4 は 3、他は 1）の多数決。**フリップ率** = 1 −（最多回答の割合）。P3（分類）と P4（採点）では、フリップ率 > 0.2（初期値（仮））を「要確認」とする。逐次早期停止（最初の 2 サンプルが一致したら 3 回目を省く等）はオプション。
- manual モードでは、プロンプトを `prompts_out/<case>/<prompt_id>_<n>.md` に書き出し、返答を `prompts_in/` から読み取る。クリップボード連携は任意（標準ライブラリのみで実現できる範囲で）。
- 送信前確認: production フラグが有効な時、外部送信の直前に人の確認（ゲート）を通す。マスキング適用後の本文を確認対象にする。
- 全呼び出しを `llm_calls` テーブルに記録（プロンプト ID、入力ハッシュ、モード、モデル名、サンプル数、所要時間、返答）。

### 9.5 DB アダプタ

| モード | 動作 | 前提 |
|---|---|---|
| csv | 人が DB で実行して出力した CSV を取り込む。エンコーディング自動判定（UTF-8／BOM 付き UTF-8／cp932）、列名マッピングは方言設定で定義 | J-PlatPat・商用DB のいずれでも使える |
| api | 商用DB の API を呼び、件数と文献リストを取得。アクセス回数上限を設定で持つ | 契約と API 仕様の確認（§16） |
| local_index | 特許情報標準データ等から作った SQLite（FTS5、trigram）を検索 | データ入手と索引構築（Phase 4 で再検討） |

共通の戻り値 `RunResult`: `query_id`、`hit_count`、`documents[]`（`doc_id`、`title`、`abstract`（あれば）、`claims`（あれば）、`codes{FI[], FT[], IPC[]}`、`pub_date`、`applicant`、`citations`（あれば））、`executed_at`、`source`。

### 9.6 知識層

| 辞書 | 内容 | 出典・作り方 |
|---|---|---|
| 分類表辞書 | FI／Fターム／IPC の各コード、タイトル、親コード、階層レベル | 特許庁提供の分類表データ（入手経路は §16）。手元にないコードは「未照合」として扱い、採用不可 |
| 同義語辞書 | 語、同義語、表記ゆれ、英訳、由来、採用回数、棄却回数 | 初期は空または社内用語集。G2 の判断で育つ |
| 分類辞書 | 観点名／語 → 採用された分類コード、採用回数 | G2 の判断で育つ |
| 調査実績 | 過去案件の入力、最終3案（DSL）、既知文献、最終適合文献 | 過去の式はパーサで DSL 化。few-shot と後方テストに使う |

SQLite。スキーマは付録C。すべての行に `created_at` と `actor`（human／llm／policy／system）を持たせる。

## 10. 中核アルゴリズム

### 10.1 適合度採点（P4）

- 入力: 文献の名称＋要約（＋請求の範囲があれば）、固定した観点定義（G1 の結果）。
- 出力（JSON）: 観点ごとの一致度 0〜3（0 無関係、1 周辺、2 一部合致、3 合致）、総合 0〜3、根拠の一文。
- 総合の既定ルール（初期値（仮））: 必須観点の一致度の最小値。調査種別ごとに変更可能。
- 適合ラベル: 総合 ≥ 2。
- n = 3 サンプルの多数決。フリップ率 > 0.2 は「要確認」として G4 で人が見る。
- 採点対象（1反復あたり、初期値（仮））: 母集団上位 K = 30 件（DB の並び順、または CAL のスコア順）＋無作為標本 m 件（§10.8）。
- 人の上書きは `judgments` に別行で記録し、集計では人の判定を優先する。
- Phase 3 以降は CAL 分類器のスコアを「安い適合度」として全母集団に付け、LLM は上位と不確実域（スコア 0.4〜0.6）のみ採点する。

### 10.2 語候補の抽出

形態素解析器が使えないため、二経路の併用とする。

1. **簡易トークナイザ**: 正規表現で「漢字の連続」「カタカナ（長音符含む）の連続」「英数字の連続」を語単位として切り出し、隣接する単位の 1〜2 連結を候補にする（例: 「高強度鋼板」「高強度」「鋼板」「焼入れ」）。汎用語リスト（装置、方法、製造、特徴、備える、前記、当該 など。初期リストを同梱し、辞書として育てる）で除去する。
2. **LLM 抽出（P2 の一部）**: 適合文献の名称・要約から技術用語を抽出させる。由来文献を必ず付ける。

両経路の候補を統合し、§10.3 の RSJ 重みで順位付けする。名称しか取れない環境では 1 の対象を名称に限定する。

### 10.3 RSJ 重みによる候補選択

母集団 U（サイズ N）の各文献に適合ラベルが付いている（採点済みの部分集合を用いる。未採点文献は分母から除く）とき、語またはコード t について

- r = t を含む適合文献数、R = 適合文献数、n = t を含む文献数、N = 採点済み文献数

とし、

```
w(t)  = log( ((r + 0.5) * (N - n - R + r + 0.5)) / ((n - r + 0.5) * (R - r + 0.5)) )
OW(t) = r * w(t)          # offer weight（追加候補の順位付け）
```

- w(t) > 0 かつ OW(t) が大きい t を「AND 軸または OR 追加の候補」、w(t) < 0 で n が大きい t を「除外・分割の候補」として提示する。
- 重み付き版（オプション）: r を Σ(適合度/3) に置き換える。
- 語とコードは同じ式で扱う。コードは文献に付く／付かないの二値素性。
- N と n は U の内側で数える（DB 全体は不可視）。したがって w(t) は「U の中での識別力」であり、根拠レポートにはその旨を注記する。
- 既知文献は適合としてカウントに含める。
- 採点済み集合は上位 K 件と無作為標本の混合で適合側に偏る。無作為標本のみで計算した w(t) も併記し、両者が食い違う候補は「要確認」とする。
- 上位 M 件（初期値（仮）: 語 30、コード 20）を G2／G4 に提示。

### 10.4 分類コードの階層集約

同じコードを複数の粒度で集計し、識別力が最大の粒度を選ぶ。

| 体系 | 粒度（粗 → 細） |
|---|---|
| FI | サブクラス → メイングループ → サブグループ → 展開記号付き → 分冊識別記号付き |
| Fターム | テーマコード → テーマ×観点 → フルコード |
| IPC | サブクラス → メイングループ → サブグループ |

- 各粒度で RSJ 重みを計算し、OW が最大、かつ n が上限（初期値（仮）: N の 50%）以下の粒度を採用する。同点なら細かい方。
- コード文字列の正規化（FI の展開記号・分冊識別記号の分離、Fターム表記の統一）は分類表辞書の書式に合わせ、Phase 0 で実データを見て確定する。

### 10.5 ブール構造化

**(a) 決定木からの式生成**

- 特徴: 語（簡易トークナイザ由来、TF ≥ 2）とコード（全粒度）の二値素性。ラベル: 適合ラベル。
- `DecisionTreeClassifier(max_depth=4, min_samples_leaf=3)`（初期値（仮））を学習し、適合側の葉に至る経路を AND 節、経路の集合を OR として DNF を得る。
- 各リテラルを由来（観点割当）に基づき観点へ振り分け、観点内 OR・観点間 AND の CNF に再構成する。振り分けに迷うものは P5 で LLM に観点を割り当てさせ、人が G2 で確認する。
- 決定木は「候補の生成器」であり、そのまま式にはしない。生成された節は変換候補として (c) に流す。

**(b) 変換操作の集合**

| 操作 | 内容 | 評価の方向 |
|---|---|---|
| ADD_TERM／DROP_TERM | 観点への語の追加・削除 | 追加は広げる（DB 実行要）、削除は狭める（局所評価可） |
| ADD_CODE／DROP_CODE | 分類コードの追加・削除 | 同上 |
| CODE_LEVEL_UP／DOWN | コード粒度の変更 | UP は広げる、DOWN は狭める |
| ADD_AXIS／DROP_AXIS | 補助観点を AND 軸に追加・削除 | 追加は狭める、削除は広げる |
| SPLIT_BLOCK／MERGE_BLOCK | 観点内の語群を2つの AND 軸に分割・統合 | 分割は狭める |
| TERM_CODE_JOIN | Block 内の語群とコード群の結合を OR ↔ AND | AND 化は狭める |
| FIELD_CHANGE | 対象フィールドの変更（TX → AB など） | 狭める方向のみ局所評価可 |
| PROXIMITY_ON／OFF | 近接演算子の付与・除去（方言が対応する場合） | 付与は狭める |
| ADD_EXCLUSION | NOT 条件の追加 | 既定で無効。有効時もプール文献を除外しないことを保証 |

- 候補の発生源: RSJ 上位（統計）、決定木の節、LLM 提案（P5。統計と現状の式を見せて意味的な提案をさせる）。発生源を記録し、後で採用率を比較する。
- **狭める方向の操作は U の手元データで局所評価**（U 内の文献を DSL で機械的に照合）し、DB 実行は不要。広げる方向の操作のみ DB 実行を要するため、1反復あたり DB 実行数を上限（初期値（仮）3）で制限する。
- 局所照合は「名称・要約に対する部分一致、コードの完全一致（粒度考慮）」で行い、DB 側の照合との差（全文フィールド、シソーラス展開など）は根拠レポートで注記する。

### 10.6 目的関数とパレート選択

各候補式 Q について

- 制約: `recall_seed(Q) = 1.0`、`recall_pool(Q) = |Q ∩ Pool| / |Pool| ≥ τ_pool`
- 目的: `minimize |Q|`、`maximize P@K(Q)`（上位 K 件の適合率。K = 30、初期値（仮））、`minimize complexity(Q)`（語数＋コード数＋Block 数）

制約を満たす候補の中でパレートフロントを取り、調査種別ごとの選択方針で 3案に割り当てる。

| 調査種別 | 選択方針 |
|---|---|
| 先行技術・無効資料 | recall_pool 最大を優先し、同点なら母集団サイズ最小 |
| 侵害予防 | recall_pool ≥ τ を満たす中で母集団サイズがレンジ内、P@K 最大 |
| 技術動向・SDI | 母集団サイズがレンジ内、complexity 最小 |

GEPA との接続: 変換操作を変異、目的をパレート軸、P5 を反省的変異（reflective mutation）として GEPA のループに載せられる。評価が検索の機械指標なので LLM-as-judge より安定する。

### 10.7 継続的能動学習（CAL）

- 特徴: `TfidfVectorizer(analyzer="char", ngram_range=(2, 3))` を名称＋要約（＋請求の範囲）に適用。分類コードは全粒度の二値素性として横に連結する。
- 分類器: `LogisticRegression(class_weight="balanced")`。
- 初期ラベル: 既知文献とプールの文献を正例。負例が無い間は無作為抽出した文献（初期値（仮）100 件）を暫定負例として扱い、判定が付いたら置き換える。
- ループ: 学習 → 未判定文献をスコア順に並べる → 上位 k 件を判定（人: k = 20、LLM: k = 50。初期値（仮））→ ラベル追加 → 再学習。
- 停止: 直近 2 バッチの適合率が閾値（初期値（仮）0.1）を下回る、予算上限、または §10.8 の推定再現率が目標到達。
- 出力: 分類器スコア（安い適合度）、係数上位の語・コード（RSJ と突き合わせて候補に加える）、プールの拡大。
- 母集団の要約テキストが取れない環境では、名称＋分類特徴のみで動かし、精度低下を根拠レポートに注記する。

### 10.8 無作為標本による再現率推定

狭い式 Q の再現率を、広め案の母集団 U を基準に推定する。

1. U から無作為に m 件抽出し（乱数シードを記録）、適合度を判定する。
2. 標本中の適合文献数を s、そのうち Q に含まれるものを t とする。
3. 推定再現率 `recall_hat(Q | U) = t / s`。信頼区間は二項比率の Wilson 区間（試行数 s、成功数 t）。
4. 適合文献の割合 `p_hat = s / m` から、U 内の適合文献総数の推定 `p_hat * |U|` も併せて示す。

- 標本サイズ: s ≥ 30 になるまで抽出、ただし m ≤ 300（初期値（仮））。s が不足する場合は推定値に「低信頼」を付ける。
- 判定の追加は無駄にしない: 標本の適合文献はプールに加える。
- **限界**: この推定は U の内側に対するもので、広め案が取り逃した文献は測れない。広め案の再現率は既知文献と引用拡張（§10.9）で担保し、根拠レポートで「U 基準の推定」であることを明記する。
- 分散低減のため、コード粒度による層化抽出をオプションで持つ。

### 10.9 引用・同族による拡張

- プール文献の引用文献・被引用文献・同族（データが取れる場合）を候補文献として取り込み、適合度を判定してプールに加える。
- 取り込んだ文献の分類コードは RSJ の入力に加える。テキストと独立した証拠として、広め案の取り逃し検知にも使う（プールの文献が U に含まれていなければ広め案の穴）。
- J-PlatPat では人が手動で確認する経路（G4 の作業項目）、商用DB では API／CSV に含まれる引用情報を用いる。

### 10.10 停止条件

§7.2 の表を Policy 決定者の既定とする。案Bでは同じ指標を G4 に表示し、人が確定する。

### 10.11 ドリフト防止

- G1 で固定した観点定義を反復中に変更しない。P4 の採点は観点定義に対して行い、直前反復の結果は採点の入力に含めない。
- 退行検知（プール文献の脱落）と初回上位適合文献の保持率を毎反復で確認する。
- 変換候補の由来を記録し、LLM 提案だけで式が変わり続けていないか（統計候補との一致率）を監視する。

## 11. 反復 1 回の処理フロー（案B基準）

```
0. 案件登録 → P1（構造化）→ G1（観点の確認・固定）
1. P2（語展開）＋辞書＋既知文献の分類集計＋P3（分類候補、辞書照合、フリップ率）→ G2（採否）
2. DSL 組立（3案）→ レンダリング＋往復検証 → G3（人が DB で実行、件数入力／CSV 取り込み）
   → 指標: |Q|（3案）、recall_seed、recall_pool
3. 採点: 上位 K 件＋無作為標本 m 件 → P4（LLM、n=3）→ 要確認フラグ → G4 前半（人が採点を確認・修正）
   → プール更新、RSJ 計算（語・コード、全粒度）、決定木、P5（LLM 変換提案）
   → 変換候補の局所評価（狭める方向）、広げる方向は次反復の DB 実行候補として保留
   → 推定再現率（Phase 2 以降）、パレートフロント、3案の更新案
4. G4 後半（確定 or 再反復）
   確定 → 根拠レポート、辞書更新、版確定
   再反復 → 2 へ（G1 の観点は変更しない）
```

案Aでは G1〜G4 を Policy が判断し、DB 実行は api モードで行う。それ以外は同一。

## 12. 評価計画

### 12.1 後方テスト（retrospective）

- **データ**: 過去案件 5〜10 件。各案件について、入力（技術説明）、人手で作った最終検索式、既知文献、最終的に適合と判断された文献リスト、可能なら当時の母集団 CSV。
- **手順**: 人手の式をパーサで DSL 化して比較対象とする。システムを案Bモードで動かし（判断は当時の記録を再現、無ければ現担当者が実施）、最終3案を得る。案Aモードは DB アクセスが確保できた案件で実施。
- **指標**:

| 指標 | 定義 | 比較対象 |
|---|---|---|
| 既知文献再現率 | 最終式が既知文献をすべて含むか | 人手の式 |
| 最終適合文献再現率 | 最終式が最終適合文献をどれだけ含むか | 人手の式 |
| 母集団サイズ | 最終式の件数 | 人手の式 |
| 反復回数・DB 実行回数 | 収束までのコスト | — |
| 人の作業時間 | G1〜G4 の合計時間 | 人手作成の所要時間（担当者見積） |
| LLM 採点と人の一致 | 適合ラベルの一致率と Cohen の κ | — |
| 候補の採用率 | RSJ／決定木／LLM 提案それぞれの候補が G2／G4 で採用された割合 | 発生源間の比較 |
| フリップ率と誤り率の相関 | 要確認フラグが実際の誤りを捕まえているか | — |

### 12.2 合成テスト

- 再現率推定器（§10.8）: 正解を知っている合成母集団で、推定値の信頼区間が真値を含む頻度（名目 95% に対して 90% 以上）を確認する。
- RSJ 計算: 手計算した 2×2 表の例と一致すること。
- レンダラ／パーサ: 全方言で往復一致。文字数上限による分割の結果が元の式と同じ集合になること（局所照合で確認）。

### 12.3 成功基準（初期値（仮））

- 最終適合文献再現率が人手の式と同等以上、かつ母集団サイズが人手の式以下となる案件が 60% 以上。
- LLM 採点と人の適合ラベルの κ ≥ 0.6。
- 案Bで人の作業時間が 30% 以上短縮。
- 統計候補（RSJ・決定木）の採用率が 30% 以上（候補生成が「見れば分かるノイズ」になっていないこと）。

### 14.2 規約

- Python 3.10 以上（Anaconda 同梱版に合わせる）。型ヒントと dataclass を使う。外部依存は §6.1 の範囲のみ。追加が必要なら実装せず §16 に起票。
- 設定は JSON（標準ライブラリで読める）。閾値・レンジ・K・m・T などの「初期値（仮）」はすべて `config/default.json` と `config/purposes.json` に置き、コードに埋め込まない。
- 乱数は全てシード付き（標本抽出、分類器の初期化）。シードを SQLite に記録し、再現可能にする。
- ネットワーク呼び出しは `pqb.llm.adapter` と `pqb.db.adapter` の 2 箇所に限定。`config.offline = true` で両者が fixtures を返す。テストは常に offline で動く。
- production フラグ: `true` の時、browser モードは起動できない。外部送信前の人の確認ゲートが有効になる。
- 文字コード: 入出力ファイルは UTF-8（BOM 付き UTF-8 は Excel 互換のため CSV 出力で選択可）。読み込みは UTF-8／BOM／cp932 を自動判定。
- ログ: `logging` モジュール。案件 ID と反復番号を全ログ行に含める。
- Excel は openpyxl。列名で照合し、セル位置に依存しない。数式は使わず値のみ。
- **してはならないこと**: J-PlatPat やその他 Web サイトへのプログラムによるアクセス（スクレイピング、自動操作）を実装しない。LLM サービスの UI 自動操作を本番コードパスに入れない。分類コードを辞書照合なしに式へ入れない。検索式文字列を LLM に直接生成させない。

### 14.3 テスト

- 単体: DSL 検証、レンダラ／パーサ往復（全方言）、RSJ（手計算例）、階層集約、局所照合、再現率推定（合成データ）、CAL（小規模合成データで正例が上位に来ること）。
- 統合: fixtures の案件を案Bモードで、Human 決定者をスクリプト化した「記録済み判断」で通す。
- 回帰: 後方テストの案件を `tests/fixtures/case_XXXX/` に置き、指標が悪化したら失敗させる。

### 14.4 成果物の受け渡し

- Phase ごとに、動作する `pqb` パッケージ、fixtures、テスト、`docs/` の更新、Excel 設計シートのテンプレート、サンプル根拠レポートを納める。
- 方言仕様や CSV 列名など「人に確認して決めた事項」は `docs/decisions.md` に日付付きで追記する。

## 15. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| J-PlatPat／LLM サービスの規約違反 | アクセス制限、コンプライアンス問題 | 自動操作を実装しない。人が実行する経路のみ。production フラグで browser モード禁止 |
| 発明情報の外部送信 | 機密漏洩 | 社内許可経路のみ。送信前確認ゲート、マスキング、送信ログ |
| LLM の幻覚（存在しない分類、誤った同義語） | 式の誤り | 辞書照合、フリップ率、由来の記録、G2 での確認 |
| CSV に要約や分類が含まれない | 逆算・CAL の精度低下 | Phase 0 で確認。取れる項目に応じた機能の段階的有効化。商用DB のエクスポートを優先 |
| クエリドリフト | 発明から離れた式に収束 | 観点の固定、観点基準の採点、退行検知、保持率監視 |
| 正解文献が乏しい案件での誤収束 | 再現率の過大評価 | 引用拡張でプールを作る。標本推定の限界を明記。人の最終確認 |
| 母集団の外側の取り逃し | 推定再現率が実態より高い | 広め案は既知文献と引用拡張で担保。推定は「U 基準」と明記 |
| 日本語トークン化の品質 | 語候補のノイズ | 簡易トークナイザ＋LLM 抽出の併用。汎用語リストを育てる。人の採否で学習 |
| 人待ちで滞留、ゲートの形骸化 | 効果が出ない | G2 は候補に統計を併記して判断を軽くする。滞留の可視化。Policy への段階移行 |
| 分類表データの入手不可 | 辞書照合ができない | 既知文献と CSV に現れたコードだけで辞書を作る縮退モード。入手経路を Phase 0 で確認 |
| LLM コスト・時間 | 運用負荷 | CAL スコアによる採点対象の絞り込み、逐次早期停止、局所評価による DB 実行削減 |

## 付録A　DSL とレンダリングの例（仮）

§9.2 の DSL（standard）を、J-PlatPat 風の論理式に仮にレンダリングした例。**実際の文法は Q3 の確認後に確定する。**

```
[高強度鋼板+高張力鋼板/AB+高強度鋼板+高張力鋼板/CL+C22C38/00/FI]*[焼入れ/AB+焼入れ/CL]
```

- Block A: 語群（AB・CL）OR コード（FI メイングループ）。Block B: 語群のみ。Block 間は AND。
- broad では Block B を外して Block A のみとし、フィールドを TX に広げる（または FI をサブクラス C22C まで粗くする）。どの軸を外すかは既定ルール（分類コードを持つ観点を残す）で決め、G2 で人が変更できる。
- narrow では Block A の語群とコード群を AND に変え、補助観点（例: 用途「自動車部材」）を Block C として追加する。

局所照合（U の手元データに対する評価）では、語は名称・要約の部分一致、コードは粒度を考慮した前方一致で判定する。

## 付録D　LLM プロンプト仕様（要件）

すべて JSON 出力。スキーマは `pqb/llm/schemas/` に置き、アダプタで検証する。few-shot 例は調査実績から生成する。

| ID | 目的 | 入力 | 出力（要点） | n |
|---|---|---|---|---|
| P1 構造化 | 発明を課題・構成・効果・用途に分解し、検索観点（必須／補助）を提案 | 入力文、調査種別 | 観点リスト（名、種別、定義、根拠となる入力文の箇所） | 1 |
| P2 語展開 | 各観点の語を同義語・上位下位・表記ゆれ・略語・英訳に展開。適合文献の名称・要約から用語を抽出 | 観点、原語、（あれば）適合文献の名称・要約 | 語、表記種別、由来（入力／文献番号）、確信度 | 1 |
| P3 分類候補 | 観点ごとに FI／Fターム／IPC 候補を提案 | 観点、語、既知文献の付与分類の集計 | コード、体系、理由。**辞書照合は Python 側で行う** | 3 |
| P4 適合度採点 | 文献を観点定義に対して採点 | 観点定義、文献の名称・要約・（あれば）請求の範囲 | 観点別 0〜3、総合 0〜3、根拠一文。**直前反復の結果は入力に含めない** | 3 |
| P5 変換提案 | 現在の式、RSJ 統計、決定木の節を見て、意味的に妥当な変換操作を提案 | DSL、統計表、変換操作の一覧 | 操作、対象、理由、予想される効果の方向 | 1 |
| P6 根拠レポート文 | 採用理由の文章化 | 観点表、統計、判断ログ | 語・分類ごとの説明文。**数値は Python 側の値をそのまま用い、LLM に生成させない** | 1 |

共通要件: 日本語出力、指定スキーマ以外の出力禁止、確信度が低い場合はその旨を明示するフィールドを持つ、入力に含まれない分類コードや文献番号を作らない（作った場合はスキーマ検証とは別に辞書・文献リストで照合して棄却）。
