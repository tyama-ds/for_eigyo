# Prism リサーチ機能 ロードマップ

更新: 2026-10-29

## 方針（全フェーズ共通）

- **依存を増やさない**: Python 標準ライブラリのみ・127.0.0.1 のみ・単一 `index.html`。Selenium は任意依存のまま。
- **ローカルLLM が第一**: OpenAI 互換のローカルLLM（Ollama / LM Studio / vLLM 等）で完結する設計にし、クラウド API も同じコードで動かす。推論系モデルの `<think>` 分離・出力規律・JSON 修復はサーバー側で吸収する。
- **出典番号 `[n]` を全生成物に通す**: レポート・会話・文書ファイル（Word / PowerPoint / PDF / Excel）のどれにも、元記事へ戻れる出典番号と URL を付ける。範囲外の番号は自動除去。
- **文書ファイルは標準ライブラリで直接組み立てる**: OOXML（docx / xlsx / pptx）は `zipfile` + XML 文字列で、PDF は自前ライターで生成する（python-docx 等を入れずに動く）。
- **非同期ジョブ + 進捗表示**: 時間のかかる処理（レポート生成・本文取得・文書生成）は共通のジョブ基盤（`/api/research/report/status`）で進捗を返し、画面を閉じても続く。
- **安全側の既定**: 本文取得は内部アドレス拒否（SSRF 対策）、書き込み API は同一オリジン確認（CSRF 対策）、描画は textContent（XSS 対策）、TLS 検証は無効化しない。

## Phase 1 — 調査レポート生成（完了 2026-10-05）

- A. map-reduce レポート生成: 選択記事全件（最大300件）をチャンク分割→並列で要点抽出→多段統合→テンプレート（概況 / 時系列 / 要点ブリーフ）に沿った Markdown。出典番号 `[n]` の検証つき。
- C. 保存と書き出し: SQLite `reports` に保存、保存済み一覧から再表示・削除、Markdown コピー / `.md` / Word(`.docx`) ダウンロード。

## Phase 2 — テーマ・新着差分・ブリーフ・本文一括取得（完了 2026-10-05）

- B. テーマ（保存した検索条件）: キーワード×情報源×期間×カテゴリに名前を付けて保存・上書き・削除。既読以降に過去ログへ入った記事数を「新着」バッジで表示し、「新着のみ表示」「既読にする」で差分確認。週次ブリーフ（直近7日）／前回以降ブリーフの一発生成。
- D. 本文一括取得: 選択記事（新しい順に最大80件）の本文を並列取得→失敗分は上限件数までヘッドレスブラウザで再試行、SQLite `pages` にキャッシュ、一覧に「本文」バッジ。レポート生成（本文も取得して要約）と会話（会話に本文を使う）に統合。

## Phase 3 — 検索の高度化と可視化（完了 2026-10-05）

- E. 検索基盤（完了 2026-10-05）: SQLite **FTS5**（trigram）の全文索引（無い環境は部分一致に自動切替）、NFKC 正規化で全角/半角・大小文字を区別しない検索、検索構文（AND / `|` OR / `-` 除外）、**同義語辞書**（リサーチ画面で編集・自動 OR 展開・展開内容の表示）、関連順（bm25）、タイトル類似による**類似記事の束ね**、**日付×情報源のヒストグラム**（クリックで期間・凡例で情報源を絞り込み）。
- F. 企業・製品ウォッチ（完了 2026-10-05）: 検索結果の見出しから固有名詞の候補を抽出（経験則＋ローカルLLM による別表記つき抽出）、「＋ウォッチ」でテーマの一種（kind=watch）として保存。新着差分・ブリーフを共用し、直近8週の件数スパークラインで推移を表示。
- G. 比較・時系列ビュー（完了 2026-10-05）: 〔A〕現在の条件 vs 〔B〕テーマ／ウォッチ／前の期間 を並べて件数・報道量・情報源・固有名詞（共通／片方だけ）を比較し、両群にタグを付けた AI 比較レポート（compare テンプレート）を生成。レポートの時系列行をタイムライン表示に切替。検索語の `"..."`（空白を含む1語）にも対応。

## Phase 4 — ドキュメント生成 × ローカルLLM（2026-10-05 追加・初版完了 2026-10-05）

実装状況: 4-0〜4-5 を `docgen.py`（OOXML / PDF の組み立て）と `server.py`（ジョブ・LLM 連携）で実装。
Word は要約＋事実表＋目次＋ヘッダー／フッター、Excel は 6 シート、PowerPoint は要点スライド＋棒グラフ＋出典、
PDF は TrueType サブセット埋め込み（自前ライター）。4-4 の経路1（ブラウザ印刷）と 4-6（読み込み）は未着手。

Claude の公式スキル（docx / pptx / pdf / xlsx）に相当する「文書ファイルを作る」機能を、**ポータル内でローカルLLMが担う形**で提供する。LLM は内容の構成・抽出・要約を担当し、ファイルの組み立ては Python 標準ライブラリで行う。

### 4-0. 共通基盤

- `POST /api/research/export` ジョブ: `kind`（docx / xlsx / pptx / pdf）、`source`（保存済みレポート id ／ 選択記事 ids ／ テーマ id）、`instructions`（「経営層向けに5枚で」「数値中心で」等の自由指示）、`audience` / `length` の既定値。進捗は既存の status API。
- 生成物は `news-portal/exports/`（.gitignore 対象）に保存し、「書き出し済み」一覧から再ダウンロード・削除。
- 会話からの呼び出し: リサーチ会話で「この結果を pptx にして」「数値を Excel に」と依頼すると、LLM が形式と指示を解釈 → 画面で確認（形式・対象・枚数）→ 生成。
- 出典番号の検証（既存 `_strip_bad_cites`）、ローカルLLM 向けの JSON 修復（コードフェンス除去・末尾切れの補修・再試行）を共通化。

### 4-1. Word（.docx）の強化

- 既存 `report_docx` を拡張: 表（事実・数値表）、ヘッダー／フッター（タイトル・作成日・ページ番号）、目次（見出しからのフィールド）、出典リスト（番号・媒体・日付・リンク）、Prism 配色のスタイル。
- LLM の役割: レポート本文に加え、要約（エグゼクティブサマリー）と「事実・数値表」の抽出。

### 4-2. Excel（.xlsx）

- LLM が記事群から**事実・数値表**を抽出（日付・情報源・企業／組織・トピック・数値・単位・出典番号・URL）。
- シート構成: 概要（条件・件数・作成日）／ 記事一覧（タイトル・媒体・日付・カテゴリ・URL・要約）／ 事実・数値（LLM 抽出）／ 情報源別・日付別の集計（Python で集計）／ 出典。
- SpreadsheetML を `zipfile` で生成: 共有文字列、セル書式（日付・数値・折り返し）、列幅、ハイパーリンク、オートフィルタ、先頭行固定。グラフ（DrawingML chart）は後続。

### 4-3. PowerPoint（.pptx）

- LLM がレポート／記事群から**スライド構成 JSON**（スライドごとにタイトル・箇条書き3〜5点・発表者ノート・出典番号）を作る。
- PresentationML を `zipfile` で生成: 表紙 → 要点 → トピック別 → 時系列 → 示唆 → 出典。図は図形で描く簡易グラフ（情報源別件数・日別件数）と表。配色・フォントは Prism のテーマを踏襲し、フッターに出典番号。
- 指示例: 「経営層向けに5枚」「技術者向けに詳しく」「1トピック1枚」。

### 4-4. PDF

- 経路1（Selenium がある場合）: レポートの印刷用 HTML をヘッドレスブラウザで PDF 化（図表・日本語フォントをそのまま使える高品質経路）。
- 経路2（標準ライブラリのみ）: 自前 PDF ライター。Windows の日本語 TrueType（Meiryo／游ゴシック／MS ゴシック）を**サブセット埋め込み**（CIDFontType2 + Identity-H）し、見出し・箇条書き・表・出典リンクを描画。フォントが見つからない環境は英数のみの標準フォントにフォールバックして注記。

### 4-5. LLM 連携の詳細

- 形式ごとのプロンプト: Excel 用の抽出スキーマ（列定義・単位の正規化・推測禁止）、PowerPoint 用の構成スキーマ（枚数上限・1枚あたり文字数）、Word 用の要約。
- 生成物の中身を先に Markdown／表でプレビュー → 承認 → ファイル化、のフローを基本とし、「そのまま作る」も選べるようにする。
- ローカルLLM は文脈窓が小さいことが多いため、レポート生成と同じ map-reduce（記事チャンクごとの抽出→統合）で表やスライドを作る。

### 4-6. 読み込み（任意・後続）

- Word／PowerPoint／Excel を「資料」としてリサーチに読み込む（OOXML から本文を抽出し、記事と同じ出典番号体系で扱う）。PDF は pypdf がある場合のみ（任意依存）。

## Phase 5 — 外部資料（RAG）と大規模レポートの堅牢化（2026-10-05 追加・完了）

利用者からの報告（200件のレポートがチャンキング後にタイムアウトする／検索結果が200件まで／外部資料も取り込みたい）への対応。

- 原因: ローカルLLMの1回あたりの記事量（3,500字）が Ollama / LM Studio 既定の文脈長 4,096 トークンを超えやすく、
  さらに並列2件を同時1件処理のサーバーに送ると待ち時間が倍になり、固定300秒のタイムアウトに達していた。
  最終統合には全メモを無制限に渡していたため、件数が多いほど文脈長超過と長考が起きやすかった。
  1チャンクの失敗でジョブ全体が失敗していた。
- 対策: 設定の「文脈長・並列数・タイムアウト」から予算を自動算出（既定 4096 / 1 / 600秒）、失敗チャンクは
  再試行→分割→スキップ、部分メモは収まるまで多段統合、進捗に経過・残り時間・失敗数、レポートに所要時間と失敗数を記録。
  検索結果の表示件数を 200〜2000 件で選択可能にし、レポートの上限を 1000 件に拡大。
- 外部資料（RAG）: PDF（pypdf）/ Word / PowerPoint / Excel / テキストを登録し、抜粋（約900字）に分けて FTS5 で索引。
  レポート・会話で問い・検索語・固有名詞に関連する抜粋を選んで記事と同じ出典番号で渡す（出典は「外部資料」）。

## Phase 6 — 続きページの取得（2026-10-09 追加・完了）

利用者からの要望（本文を URL で取得すると1ページ目だけで、続きがある記事がある。生成AIで判断して続きを取りたい）への対応。

- 規則（rel=next・ページ番号だけが違う URL・ページャの文言・「全文表示」）で続きをたどり、決めきれないときだけ
  生成AIに候補リンクのどれが続きかを**番号で**選ばせる（候補は同じサイト・内部アドレスでない URL に限る）。
  最大ページ数・時間・有料／ログイン・別記事・再訪で止め、理由を記録する。Yahoo!ニュースの `/pickup/` は記事本体へ1ホップ。
- 本文の取り出しを段落単位にし（本文の器を優先・nav/aside/footer を除く・文字コード判定）、2ページ目以降は重複段落を除いて連結。
  保存上限を 24,000 字に拡大し、レポート・会話には「冒頭＋問いの語を含む文」の抜粋を渡す（続きの関連箇所が届くように）。
- ヘッドレスブラウザ経由でも同じ規則でたどり、ページ内の「続きを読む」ボタンを押してから読む。
- 設定（自動／規則のみ／1ページ目だけ・最大ページ数）、一覧の「本文 3p」、完了表示の集計と「取り直す」。
- 後続: Google ニュース経由のリンク（JS リダイレクト）の解決、サイトごとの判定結果の学習（AI 判定の回数削減）、
  長い本文の記事ごと要約（AI）による圧縮。

## Phase 7 — 大規模レポートのタイムアウト対策（2026-10-14 追加・完了）

利用者からの報告（200件のレポートがやはりタイムアウトする）と要望（1回の出力で収まらない・タイムアウトしそうな
ときは複数回に分けて出力する）への対応。

- 原因（模擬ローカルLLMで再現）: 統合・最終段の入力が回答と思考の分を空けておらず、文脈長 4096 では
  入力＋回答＋思考がはみ出して生成が止まらなくなり、非ストリーミングの固定タイムアウトに達していた
  （部分要約は終わっているのに最終段で失敗し、それまでの結果も失われた）。設定の文脈長が接続先より大きい場合も同様。
- 対策: ストリーミング受信（最初の文字までと生成中の停止を分けたタイムアウト、回答・思考の上限で打ち切り）、
  回答と思考の分を空けた予算、最終段の「1回／見出しごと」の自動判定（文脈長・実測の速さ・失敗や書き切れなさ）と
  続きを書かせる仕組み、推論モデルの思考の抑制と実測による適応、途中結果の保存と同じ条件での再実行、
  最終段の失敗時に抽出結果を残す、接続先の診断（実際の文脈長・速さ・思考の有無）。
- 模擬（文脈長 4096・生成 20 トークン/秒・思考 1,200 トークン）での 200 件: 従来は約1時間後に最終段で失敗、
  対策後は約0.2時間で完了。思考を抑えられないモデルでも完了（約1.3時間）。設定の文脈長が接続先より大きい場合、
  従来は約13時間後に失敗、対策後は約0.3時間で完了。
- レビュー（21件の指摘を再現・修正）: 長さ切れ・接続先のエラー・途中で切れた応答を成功として扱っていた、
  閉じタグだけを書くモデルの思考を回答として数えていた、回答の上限が予算と違う物差しで文脈長を超え得た、
  続きページの判定（90秒）が600秒まで延びていた、通常の再生成でも古い途中結果を返していた、再実行で実測が
  失われて分け方が変わっていた、見出しの取り出しで小見出しが落ちた、診断が別モデルの文脈長を示した、など。

## Phase 8 — 過去ログタブ（2026-10-20 追加・完了）

利用者からの要望（過去ログも検索できるようにしたい。新しいタブ・アイコンから、リスト／パネル表示を切り替えて
時期やキーワードで検索したい）への対応。リサーチ画面（AI に渡す作業ウィンドウ）とは別に、過去ログをフィードと
同じ感覚で読むための一級の画面として作った。

- 入口: トップバーの 過去ログ アイコン（`H`）とカテゴリ列の末尾の「過去ログ」タブ。メイン画面を切り替えるだけで、
  フィードは裏で更新され続け、「フィードに戻る」・`Esc`・カテゴリの選択・ブラウザの「戻る」で元のスクロール位置に戻る。
- 検索条件: キーワード（AND / OR / 除外 / 同義語展開・ハイライト）× 期間ボタン（今日〜1年・すべて、既定30日）または
  日付範囲 × 情報源 × カテゴリ、新しい順／関連順。条件は URL ハッシュと sessionStorage に残し、再読み込みで復元。
- 表示: リスト（日付・情報源・タイトル・短い要約）とパネル（フィードと同じカード）を切替（`L`、フィードとは別に記憶）。
  「N 件（全 M 件中）」と保存期間、読み込み中・空・エラーの表示、30件ずつの「さらに読み込む」。
- API: `GET /api/archive/search` に `offset` と応答の `total`・`offset`・`limit`・`has_more` を追加（既存の項目・呼び出しは
  そのまま）。総数は検索と同じ WHERE 句で数え、並びに rowid を加えて同時刻の記事でもページの境目で重複・欠落しない。
  2万件の過去ログで件数＋1ページの取得は 0.1 秒程度。
- 後続: 一覧からの複数選択→リサーチ／レポートへの受け渡し、類似記事の束ね表示、期間ヒストグラムでの絞り込み。

## 不具合修正 — 壊れたフィード1件で記事一覧全体が止まる問題（2026-10-20）

- 症状: 記事が表示されず「情報源がありません」、再取得で「読み込みに失敗しました」（`/api/articles` が応答なし）。
- 原因: フィードの XML 解析エラー（ET.ParseError）をどこでも受け止めておらず、1件の情報源が壊れた XML を
  返すと記事の取得全体が例外で中断していた（8月以前からの潜在的な不具合。配信元の変化で表面化）。
- 対策: 解析エラーは情報源ごとのエラーにする、よくある壊れ方は修復して読む、情報源ごとの想定外の例外も
  隔離する、リクエスト処理の例外は 500 と理由を返す、記事の取得に失敗しても情報源パネルを表示する、
  診断・接続テストに解析エラーを表示する。

## 保守 — feeds.json の読み込みを堅牢化（2026-10-20）

利用者からの報告（更新後に「情報源がありません」となりフィードを取らない。feeds.json に中身はある）への対応。
従来は文字コード（Shift_JIS・BOM つき UTF-8）・JSON の書式の誤り・Git の競合の印・ほかのプログラムによるロックのどれでも
黙って空の一覧として扱い（画面は「情報源がありません」・取得 0 件）、その状態で情報源を追加すると、その1件だけの一覧で
上書きしてファイルの中身を消していた。

- 読み込みの許容: BOM の有無を問わない UTF-8、Shift_JIS（cp932）・UTF-16（BOM つき）は読み込んで注記（次の保存で UTF-8 に）、
  一覧だけ（`[ … ]`）の形、`url` の無い要素は読み飛ばして件数を注記（保存時も消さない）。JSON の推測修正はしない。
- 使えないときは理由（種類・日本語の対処・行と文字の位置・該当行と直前の行・ファイルの場所）を `/api/articles`・`/api/sources` の
  `sources_problem` で返し、画面上部の帯・状態欄・情報源画面に表示。コンソールにも1行警告（cp932 のコンソールでも落ちない）。
- 読み込めない間の書き込みは 409 で断る。「初期の情報源に戻す（今のファイルは控えを残す）」（`POST /api/sources/restore-defaults`）は
  `feeds.json.broken-日時` に控えてから初期の情報源を書き出す（情報源 0 件のときも使える）。

## 改善 — 過去ログの保存件数・期間を設定で選べるように（2026-10-23）

利用者からの質問（過去ログが 2万件しか出ない）への対応。過去ログは 2万件で固定の上限があり、保存のたびに古い記事を
削除していた。

- 設定画面に「過去ログの保存」を追加: 件数で残す（最新 N 件・1,000〜2,000,000）／期間で残す（直近 N 日・7〜3,650）／無制限。
  既定を最新 10万件に引き上げ（設定していない既存の環境も更新で 10万件になり、余分には消えない）。
- 下げるときは、今の状況（件数・最古の日付・ファイルの大きさ）と「この設定では古い記事 N 件が削除されます（元に戻せません）」を
  入力に合わせて表示し、保存の前に件数を確認してからすぐに削除（`GET /api/archive/retention` で事前に数える・何も変更しない）。
  すでに削除された記事は戻らない。過去ログタブの件数欄に保存の設定を表示。ページ送りの 2万件の頭打ちも外した。
- 削除は対象の記事とその全文索引・本文キャッシュの行だけにし、保存のたびの COUNT(*)・表全体の NOT IN をやめた
  （件数の控え＋索引の端から読む）。20万件で 50件の保存は 10〜30 ms 程度、20万件→10万件の削除は約2秒。
- レビュー指摘の修正: settings.json を読めない・壊れている・保存の設定が不正なときは既定と取り違えて消さず削除を止める
  （警告・画面に理由。読めない間は設定と同義語の保存も 409 で断り、APIキー・保存の設定を消さない）。まとめての削除は
  2,000 件ずつロックを手放して行い（50万件でも検索・取得の待ちは 0.2 秒程度）、取得の保存は設定をロックの中で読む
  （保存した直後の取得が古い設定で消さない）。上げる・同じ設定では少しの超過も保存では消さず、文言を実際の動きに合わせた。
  数値の欄の Enter で保存しない・ラジオのフォーカスの輪・「残るのは」の行のコントラスト・読み上げ領域を作り直さない。
  本文キャッシュは過去ログにある記事の分だけ保存し、以前の残りは適用時と5分に1回掃除する。
- レビュー2回目の修正: 保存した・読めた保存の設定を archive.sqlite3 にも控え、settings.json が無くなっても既定の 10万件で
  消さない（409 の案内もファイルを移すよう勧めない）。settings.json を読めないときの既定値で入れた設定画面・同義語辞書は
  保存させず（消えない警告・「読み込み直す」）、保存の設定は欄を操作したときだけ送る（値が不正なときも方式を選ばない状態で
  開く・キャンセルは「保存を取り消しました」）。止めている間は既定を今の設定として出さず、過去ログタブに理由を文字で出す。
  裏の削除は待っている保存に必ず譲る（世代番号でなく待ちの数）、DB を開けなくても applying を残さない、読み取り中の別の接続が
  あっても -wal の縮小で待たない、settings.json の読み書きを通しで直列化、commit の失敗で件数の控えを数え直す、
  無制限の「1万件あたり」は削除の前に測った大きさで出す。

## 保守 — アイコンを同梱（2026-10-29）

利用者からの要望（アイコンファイルも同梱してほしい）への対応。これまでタブのアイコンは index.html に埋め込んだ図だけで、
ファイルとしては無かった。

- `icons/` に、ヘッダーの図柄（プリズムと分光）を濃紺の角丸タイルに載せたアイコンを追加: `prism.ico`（16〜256 px の7枚。
  64 px 以下は 32bit BMP、128・256 px は PNG）、`prism.svg`（元の図柄）、`prism-small.svg`（16〜48 px 向けに線を太くした版）、
  PNG（16・32・48・192・512）、スマートフォン・インストール用の四隅まで塗った版（`prism-180.png`・`prism-maskable-*`）。
- サーバーは `/favicon.ico`・`/icons/<名前>`・`/manifest.webmanifest` を返す（`icons/` 直下の英小文字・数字・ハイフンの名前だけ。
  `../` などで外のファイルは読ませない）。index.html はこれらを参照し、Edge / Chrome の「アプリとしてインストール」に対応
  （タイトルバーの色は表示テーマに合わせて切り替え）。
