# Doc Vault — 文書管理 × RAG 相談

PDF・Word・PowerPoint・Excel などの文書を取り込むと、**全文検索・埋め込み・ナレッジグラフ・文書要約**の
4種類の索引を自動で作り、生成 AI との相談窓口から**出典付き**で質問に答えるアプリ。
質問の種類（事実・関係・要約・比較・雑談）を判定して、検索方法を自動で切り替える。

```bash
pip install pypdf anthropic          # PDF を扱う / Claude を使う場合（どちらも任意）
python doc-vault/server.py           # http://127.0.0.1:8760
python doc-vault/server.py --open    # 起動後にブラウザを開く
```

起動したら「文書」タブで **サンプルを読み込む**（公開資料2件・社外秘資料2件）→「設定」タブで LLM を登録 →
「相談」タブで質問、の順で試すのが早い。LLM 未設定でも全文検索と、回答の代わりの関連箇所の抜粋は動く。

## できること

| 画面 | 内容 |
|---|---|
| 相談 | チャットで質問すると、文書を検索して出典（[S1] 文書名 p.3 など）付きで回答。出典をクリックすると原本（PDF は該当ページ）や本文の該当箇所を表示。相談ごとに「範囲」（フォルダ・特定の文書）と「モード」（自動 / ローカルのみ / クラウド）を選べる。文書を使わない一般的な相談にも答える |
| 文書 | ドラッグ＆ドロップで取り込み（PDF / DOCX / PPTX / XLSX / TXT / MD / CSV / HTML）。フォルダ・タグ・区分（社外秘 / 公開）で管理。全文検索、取り込み状況（索引ごとの完了状態・警告）、編集・再処理・削除 |
| グラフ | 取り込み時に抽出したエンティティ（組織・人物・製品・設備・規格…）と関係のグラフ。ズーム・検索・クリックで関係と出典文書を表示。文書ごとに絞り込める |
| 設定 | ローカル / クラウドの2系統の LLM 接続、データの取り扱い、RAG の各機能の ON/OFF |

## LLM の使い分け（社外秘はローカル、公開資料はクラウド可）

接続先は2系統を登録する。

- **ローカル LLM**: 社外秘文書を送ってよい接続先（Ollama / LM Studio / vLLM / 社内 Azure OpenAI など）
- **クラウド LLM**: 公開文書だけを扱う接続先（Claude / OpenAI / Gemini / Azure OpenAI）

文書には取り込み時に**区分（社外秘 / 公開）**を付ける（既定は社外秘）。

| 処理 | 社外秘の文書 | 公開の文書 |
|---|---|---|
| グラフ抽出・要約 | ローカル LLM | クラウド LLM（設定でローカルにも変更可） |
| 埋め込み | ローカルの埋め込みモデル | クラウドの埋め込みモデル（未設定ならローカル） |
| 回答 | 根拠に社外秘を1件でも含めばローカル LLM | 公開資料だけならクラウド LLM（自動モード） |

**社外秘のデータをクラウドへ送る呼び出しは、プログラム側で必ず止まる**（`PolicyError`）。設定を誤っても漏れない。
テスト（`tests/test_api.py`）では、モック LLM への全送信を記録して、クラウド側のモデルに社外秘の本文が
一度も届いていないことを確認している。

相談のモード:

- **自動**（既定）: 社外秘資料を根拠に含む回答はローカル、公開資料だけならクラウドで回答。
  補助処理（質問の分析・根拠チェック）はローカル優先。社外秘を参照した相談は以後ずっとローカルで処理する
- **ローカルのみ**: 質問文も含めて外部に送らない
- **クラウド**: 社外秘文書を検索対象から外し、公開文書だけでクラウドが回答する

## 採用した RAG 手法と、この用途に合う理由

文書管理の相談では「特定の数値や手順を聞く」「人・組織・設備のつながりを聞く」「資料全体をまとめさせる」
「比べさせる」が混在する。1つの手法ですべてに強いものは無いため、取り込み時に複数の索引を作り、
**質問ごとに手法を選ぶ**構成にした（2026 年時点の実務での主流もこの「ルーター＋ハイブリッド」構成）。

```
取り込み: 抽出（ページ・スライド・シート・見出し単位）→ チャンク → 全文索引（BM25）→ 埋め込み
          → ナレッジグラフ（エンティティ・関係・上位概念キーワード）→ 文書要約
相談:     質問ルーター → 戦略別の検索（DecisionRAG / Hybrid / グラフ / 要約）→ 根拠の十分性チェック
          （不足なら再検索）→（再順位付け）→ 出典付き回答
```

| 手法 | どこで使うか | 選んだ理由 |
|---|---|---|
| 構造を保ったチャンク分割＋文脈ヘッダ（Anthropic の Contextual Retrieval の軽量版） | 取り込み | PDF はページ、PPT はスライド、Excel はシートと行範囲、Word は見出しで分け、各チャンクに「文書名 > 見出し」を付けて索引化。出典をページ・スライド単位で示せる |
| **DecisionRAG**（検索器を使わず、文書の階層を判定モデルでたどる。下の節を参照） | 事実・比較の質問 | 文書管理はフォルダ・文書・見出し・ページという階層を元から持つため、論文の「コーパスの構造をたどる」方式がそのまま使える。字句や埋め込みの近さでは拾えない言い換え・否定・条件を、判定モデルが候補を見比べて判断する |
| Hybrid 検索（BM25 + 埋め込み、RRF で融合） | 事実の質問・全般 | 型番・社内用語は字句一致（BM25）、言い換えは埋め込みが強い。日本語は形態素解析なしの文字バイグラムで扱う |
| GraphRAG / LightRAG 方式のグラフ抽出（**文書単位で増分更新**） | 取り込み | 文書が増え続ける用途なので、全体の作り直しが要らない LightRAG の増分更新の考え方を採用。関係の端点が抜ける LLM の癖は自動補完 |
| HippoRAG 2 の Personalized PageRank | 関係・経緯の質問 | 質問に出る対象を起点にグラフ上で関連度を広げ、2〜3段先の関係（A社→製品→工場）に関わる箇所も拾う |
| LazyGraphRAG 方式のコミュニティ要約（**質問時に必要な分だけ要約**） | 全体の要約・傾向 | 本家 GraphRAG は取り込み時に全コミュニティを要約するため費用が大きい。関連するテーマだけ質問時に要約してキャッシュする |
| RAPTOR 方式の文書要約（部分要約 → 全体要約の2層） | 要約・横断の質問 | 「この資料の要点」「資料全体の傾向」に、チャンクの断片ではなく文書単位の要約で答える |
| 質問ルーター（Adaptive-RAG。検索要否の判定は D2-RAG 等と同じ発想） | 相談の入口 | 質問の種類で検索方法を選び、挨拶・言い換え依頼では検索しない（無関係な資料の混入を防ぐ）。会話履歴から「それ」「この資料」を補った単独の質問に書き換える |
| マルチクエリ（RAG-Fusion） | 比較の質問 | 比較対象ごとに検索して融合し、片方の資料だけに偏らないようにする |
| CRAG（Corrective RAG） | 事実・関係・比較 | 取得した資料で答えられるかを LLM が判定し、不足なら書き換えた検索文で1回だけ再検索 |
| LLM による再順位付け（任意） | 全般 | 精度は上がるが LLM 呼び出しが増えるため既定は OFF |

使わなかったもの: 本家 GraphRAG の取り込み時の全コミュニティ要約（費用）、Self-RAG（専用学習モデルが必要）、
ColBERT 等の専用検索モデル（依存が重い）。比較・評価は [RAG Orchestrator](../rag-orchestrator/) で行える。
## DecisionRAG（検索器を使わない階層ナビゲーション）

Wan, Jünger, Du, Liu, Krishnan, Weinberger（Cornell University / ASAPP）
"Retriever-Free Retrieval: Navigating Documents with Decision Models"
（[arXiv:2610.35868](https://arxiv.org/abs/2610.35868)、2026-10-26）の方式を実装した。

- **考え方**: 第1段の検索器（BM25 / 埋め込み）を使わず、図書館で棚を順にたどるように、
  コーパスの階層を上から下へ判定モデルでたどる。各段では候補を**同じ文脈に並べて一度に**判定させる
  （候補どうしを見比べるので、関連度の尺度がそろう）。上位の枝だけを残して下の段へ進む
- **論文の結果**（著者報告）: 課題向けの学習なし・第1段の検索器なしで、密ベクトル検索＋8B リランカーを
  MultiDoc2Dial で R@1 +13.8 ポイント、Natural Questions で Hit@1 +17.4 ポイント上回った。
  1質問あたりの検索時間は中央値 0.7〜1.8 秒
- **判定モデル**: 論文は TypeSafe の判定専用モデル **Jev**（テキストを生成せず、yes/no の確率や
  選択肢ごとの確率を返す）を学習なしで使っている。公開コードは無い

### この実装

| 論文の要素 | Doc Vault での実装 |
|---|---|
| コーパスの階層 | フォルダ → 文書 → 節（見出しのまとまり。見出しが無い PDF は数ページずつ）→ 段落（チャンク）。子が 24 を超えるノードは、埋め込みがあれば k-means（論文も NQ では埋め込み＋k-means で階層を作っている）、無ければ並び順で中間ノードに分ける。子が1つだけのフォルダは飛ばす |
| ノードの説明文 | フォルダ: 名前・配下の文書名・主なキーワード ／ 文書: タイトル・文書要約・キーワード（要約が無ければ見出しと冒頭）／ 節: 見出し・ページ範囲・冒頭 ／ 段落: 本文 |
| 各段の二値判定（共有文脈・1回で全候補） | **Jev**: OpenRouter Decisions API で、候補一覧を `state` に入れ、候補ごとの `noul`（関連する確率）を1リクエストで求める（最大 50 件ずつ）。**LLM**: ローカル / クラウドの LLM に候補を並べて 0〜9 で採点させ、logprobs が取れる接続先（OpenAI 互換・Azure）では採点の数字の確率分布から期待値を求める（≒ 確率）。Claude など logprobs の無い接続先は出力された数字を使う |
| 残す枝（ビーム） | 確率 0.3 以上を上位 4 本まで（設定で変更可）。どれも満たさないときは、閾値で切らずに順位で上位 2 本の探索を続ける（枝刈りは取り消せないので再現率寄りにする） |
| 段落の選び方 | 閾値で切らず確率順に上位を返す（固い閾値は正解を黙って落とすという、公開実装の検証で繰り返し出た教訓に従う） |
| 選択式の並べ替え（multiple-choice） | 上位 20 件までを「どれが最も答えを含むか」の選択式で比べ、その確率で並べ替える。Jev は `choice` 質問、LLM は記号 A〜T の1文字を答えさせてその確率を読む |
| 判定回数の上限 | 1質問あたり 8 回（設定で変更可） |
| 新しい文書の追加 | フォルダの位置に入るだけ。再学習・全体の作り直しは不要 |

使い方:

- 相談ごとに「検索」で **自動 / DecisionRAG / 従来型** を選ぶ。
  - 自動: 事実・比較の質問で DecisionRAG と Hybrid 検索を融合する（論文も補完として密ベクトル検索の併用を挙げている）
  - DecisionRAG: 論文どおり第1段の検索器を使わない
  - 従来型: 使わない
- 回答の「検索の流れ」に、各段で残った枝とその確率が表示される
- 設定タブ → RAG の設定 → DecisionRAG で、判定モデル（LLM / Jev）・各段で残す枝の数・判定回数の上限・
  選択式の並べ替えを変えられる

Jev を使う場合（任意）: [OpenRouter](https://openrouter.ai/) の API キーを「Jev の接続」に入れ、判定モデルを
「Jev」にする。モデルの既定は `typesafe/jev-1.14`（日本語を含む多言語の改善をうたう版。論文は 1.13 を使用）。
Jev は外部サービスなので、**候補がすべて公開文書の段だけ**を Jev で判定し、社外秘を1件でも含む段はローカル LLM で
判定する（この区別はプログラム側で強制し、テストで送信内容を検査している）。

違いと注意:

- LLM で判定する場合は、論文のように「1回の計算で全候補の確率を読む」のではなく、候補ごとに1桁の数字を
  出力させて読む近似。Jev より遅く、ローカル LLM では1段に数秒〜数十秒かかる
- 精度はノードの説明文に左右される（論文も限界として挙げている）。文書要約を作っておくと文書段の判定が良くなる
- 1段目で外れた枝は二度とたどらない（論文の限界と同じ）。自動モードでは Hybrid 検索との融合で補う
- Jev は英語が最も得意で、日本語の文書での精度は未確認

## 接続設定の例

「設定」タブのプリセットボタンで入力欄が埋まる。

| 用途 | 種類 | Base URL | モデルの例 |
|---|---|---|---|
| ローカル（Ollama） | OpenAI 互換 | `http://127.0.0.1:11434/v1` | `qwen3:14b`、埋め込み `bge-m3`（日本語に強い） |
| ローカル（LM Studio） | OpenAI 互換 | `http://127.0.0.1:1234/v1` | 読み込んだモデル名 |
| クラウド（Claude） | Anthropic | 空（既定） | `claude-opus-5-5`（取り込み用に別モデルも指定可） |
| クラウド（OpenAI） | OpenAI 互換 | `https://api.openai.com/v1` | 埋め込み `text-embedding-3-small` |
| Azure OpenAI | Azure | `https://<リソース名>.openai.azure.com` | デプロイ名 |

- Claude は公式 SDK（`pip install anthropic`）で呼ぶ。API キーは設定画面か環境変数 `ANTHROPIC_API_KEY`。
  安全上の理由で回答を辞退された場合は、サーバ側の自動フォールバック（`fallbacks: "default"`）で別モデルが答える
- Claude には埋め込み API が無い。クラウド側の埋め込みは OpenAI 互換の API を指定するか、空欄にする
  （空欄でも全文検索とグラフで検索できる）
- 推論モデル（Qwen3 / DeepSeek-R1 系）の `<think>…</think>` は回答から取り除く
- 社内ネットワークでは、クラウド側は「プロキシを使う」を ON（既定）にして環境変数 `HTTPS_PROXY` を使う

設定は `doc-vault/docvault.config.json`（API キーを含むため gitignore 済み）に保存される。

## 共有して使う（将来）

今は個人利用を想定しているが、共有に向けて次を用意してある。

- `--host 0.0.0.0` で LAN に公開すると**アクセストークン必須**になる（`--token` で指定、省略時は自動生成して表示）
- `--data-dir` でデータ（SQLite・原本）を共有フォルダやサーバの任意の場所に置ける
- 文書・相談のデータに所有者（owner）と公開範囲（visibility）の列を持っている（現状は `local` 固定）。
  利用者ごとの権限（部署単位の閲覧制限など）は今後の課題

## データの保存先

```
doc-vault/data/              （--data-dir または環境変数 DOCVAULT_DATA で変更）
  docvault.sqlite3           文書メタデータ・チャンク・埋め込み・グラフ・相談履歴
  files/<文書ID>.<拡張子>     原本
```

## テスト

```bash
cd doc-vault
python -m unittest discover -s tests -v
```

- 実 LLM 不要。`tests/mock_llm.py`（OpenAI 互換・ストリーミング対応の決定論的モック）を使う
- 抽出（DOCX / PPTX / XLSX / PDF / CSV / HTML / MD / 文字コード）、検索部品、設定の検証、
  Claude 呼び出しの形（偽の SDK で検査）、グラフ（端点補完・PPR・コミュニティ・区分の伝播）、
  DecisionRAG（階層の構築と分割・logprobs からの確率・ナビゲーション・Jev の要求形式と分割・古い DB の移行）、
  API 統合（取り込み → 検索 → 相談の各モード → グラフ → 編集・削除）、社外秘がクラウドへ送られないことの検証
- PDF のテストは pypdf か PyMuPDF があるときだけ実行される

```
  retrieval.py            検索インデックス（BM25 + 埋め込み空間ごと）と Hybrid 検索

  rag.py                  相談パイプライン（ルーター・戦略別検索・CRAG・再順位付け・回答・出典）
  decision.py             DecisionRAG（階層の構築・共有文脈の判定・ビームでのナビゲーション・選択式の並べ替え）
  jev.py                  判定モデル Jev のクライアント（OpenRouter Decisions API。公開文書の候補のみ）
  samples.py              サンプル文書と DOCX / XLSX / PPTX / PDF の最小生成器
static/                   画面（index.html / app.js / style.css / graphview.js）
tests/                    ユニット + API 統合（モック LLM）
```

`static/graphview.js` は [RAG Orchestrator](../rag-orchestrator/) と共通のグラフビューア

## 既知の制約

- スキャン画像の PDF（文字が埋め込まれていないもの）は OCR が必要で、現状は取り込めない（警告を表示）
- 図・グラフ・画像の中身は読まない（テキストと表のみ）
- 埋め込み検索は総当たり（numpy があれば高速化）。目安として数万チャンクまで
- 区分を「公開 → 社外秘」に変えても、それまでにクラウドへ送った内容は取り消せない（以後の処理がローカルになる）
