# Doc Vault — 文書管理 × RAG 相談

PDF・Word・PowerPoint・Excel などの文書を取り込むと、**全文検索・埋め込み・ナレッジグラフ・文書要約**の
4種類の索引を自動で作り、生成 AI との相談窓口から**出典付き**で質問に答えるアプリ。
質問の種類（事実・関係・要約・比較・雑談）を判定して、検索方法を自動で切り替える。

```bash
pip install pypdf anthropic          # PDF を扱う / Claude を使う場合（どちらも任意）
python doc-vault/server.py           # http://127.0.0.1:8760
python doc-vault/server.py --open    # 起動後にブラウザを開く
```

**Windows では** `doc-vault\start.bat` を**ダブルクリック**するだけでよい。

- Python（`py -3`、無ければ `python`）を探して起動し、ブラウザを開く。すでに起動していれば開くだけ（二重には起動しない）
- 初回に pypdf が入っていなければ、`requirements.txt`（pypdf と anthropic）を入れるかを聞く（60 秒答えなければ入れずに起動）。
  社内ネットワークで pip がつながらないときは `py -3 -m pip install --proxy http://プロキシ:8080 -r doc-vault\requirements.txt`
- オプションはそのまま渡る（例: `start.bat --port 8761`、`start.bat --data-dir D:\docvault-data`）
- デスクトップから使うときは、bat をコピーせずショートカットを作る。App Portal（`launcher\start_portal.bat`）のカードからも起動できる
- 使用中のポートで起動しようとすると、別のアプリが使っている旨と `--port` の例を表示して止まる

起動したら「文書」タブで **サンプルを読み込む**（公開資料2件・社外秘資料2件）→「設定」タブで LLM を登録 →
「相談」タブで質問、の順で試すのが早い。LLM 未設定でも全文検索と、回答の代わりの関連箇所の抜粋は動く。

## できること

| 画面 | 内容 |
|---|---|
| 相談 | チャットで質問すると、文書を検索して出典（[S1] 文書名 p.3 など）付きで回答。**相談先**（どのフォルダ・文書に聞いているか）を画面上部に常に表示し、「相談先を変える」でフォルダ（複数可）と文書を選ぶ。**検索方式**（自動 / 速さ優先 / 選んで使う…）と**使う RAG**（全文・埋め込み・GraphRAG・DecisionRAG…）を相談ごとに選べる。回答ごとに、相談先・使った RAG・回答した LLM を表示。出典にマウスを載せると**採用の根拠（どの検索で何位・スコア）**が出る。🎤 で**音声入力**（文字起こし） |
| 文書 | ドラッグ＆ドロップで取り込み（PDF / DOCX / PPTX / XLSX / TXT / MD / CSV / HTML）。**フォルダごと取り込み**（サブフォルダの構成のまま）。**フォルダツリー**（開閉・作成・名前の変更・削除）で、文書の行やフォルダを**ドラッグして移動**。複数選択して一括で移動・区分の変更・質問・再処理・削除。文書ごとに**どの LLM で読み込んだか**を表示し、LLM ごとの結果を残して選べる |
| グラフ | 取り込み時に抽出したエンティティ（組織・人物・製品・設備・規格…）と関係のグラフ。ズーム・検索・クリックで関係と出典文書を表示。フォルダ・文書ごとに絞り込める |
| 設定 | ローカル / クラウドの2系統の LLM 接続、データの取り扱い、RAG の各機能の ON/OFF、**グラフの作り方**（標準 / 高速 / LLM なし）、音声入力 |

## 相談先（どの文書に聞いているか）

相談の画面の上部に「相談先」（例: 📁 社内/品質 ＋ 📄 SkyEdge 仕様書 → 7 文書（社外秘 5・公開 2））を常に表示する。

- 「相談先を変える」で、フォルダ（配下を含む・複数可）と個別の文書を組み合わせて選ぶ（フォルダか選んだ文書のどれかに
  入る文書が対象）。何も選ばなければすべての文書。選んでいる途中で対象の文書数と一覧が出る
- 新しい相談は「すべての文書」から始まり、空の画面に「どの文書に聞きますか？」とフォルダ・最近の文書のボタンが出る
- 相談の履歴の各行にも相談先を出す。履歴を切り替えると相談先の枠が光り、相談先も切り替わったことが分かる
- 回答ごとに、その時の相談先と文書数を記録して表示する（途中で相談先を変えても、どの回答がどこに聞いたものか分かる）
- 質問欄にも「📁 社内/品質（7 文書）に質問」と出る。クラウドモードでは公開文書だけが対象になる旨も出る

## 採用の根拠（出典のスコア）

回答の出典（[S1] や出典カード）にマウスを載せると、その資料がなぜ選ばれたかを表で出す。

| 表示 | 意味 |
|---|---|
| 検索ごとの順位・スコア | DecisionRAG（経路スコア: たどった各段の判定確率の幾何平均）、ハイブリッド（BM25 と埋め込みの RRF）とその内訳の BM25 スコア・埋め込みのコサイン類似度、GraphRAG（Personalized PageRank のスコア）、マルチクエリ |
| 統合スコア（RRF）・総合順位 | 各検索の順位 r から 重み÷(60＋r) を足した値。DecisionRAG・関係の質問のグラフは重み 1.5 |
| 再順位付け・再検索 | LLM の再順位付けでの順位（元の順位）、根拠不足の再検索（CRAG）で加わった資料か |
| 回答で引用 | 回答の本文で [S1] と引用されたか |

文書要約（D）はその BM25 スコア、コミュニティ要約（C）はメンバーの語の一致のスコアを出す。

## 検索方式（使う RAG を選ぶ）

相談の「検索方式」と「使う RAG」で、どの RAG を使うかを相談ごとに選べる（新しい相談の既定は設定タブ、
または相談画面の「この方式を既定にする」）。質問の時間を左右するのは検索そのもの（どれも 1 秒以内）ではなく
**LLM の呼び出し回数**なので、画面に 1 問あたりの回数の目安を出す。

| 検索方式 | 使う RAG | 1 問の LLM 呼び出し（既定の設定） |
|---|---|---|
| 自動（おすすめ） | 質問の種類で使い分け: 事実・比較 → DecisionRAG＋ハイブリッド、関係 → GraphRAG＋ハイブリッド、要約 → 文書要約＋コミュニティ要約。ルーター・根拠チェックあり | 最大 12 回（事実の質問で DecisionRAG を使うとき） |
| 速さ優先 | 全文（BM25）＋埋め込み＋GraphRAG を毎回。ルーター・根拠チェックを省く | 1 回（回答だけ）＋埋め込み 1 回 |
| 選んで使う | 「使う RAG」でチェックした方式を、質問の種類にかかわらず毎回使う | 選んだ方式による（画面に表示） |
| DecisionRAG のみ | 検索器を使わず階層を判定でたどる（見つからなければ全文検索で補う） | 最大 12 回 |
| 従来型 | 自動から DecisionRAG を除いたもの | 最大 7 回（要約の質問でコミュニティ要約を作るとき） |

「使う RAG」で選べる方式:

| 方式 | 1 問あたり | 向いている質問 |
|---|---|---|
| 全文（BM25） | LLM 0 回 | 型番・社内用語・固有名詞（語の一致）。最速 |
| 埋め込み（ベクトル） | 埋め込み 1 回 | 言い換え・意味の近さ |
| GraphRAG | LLM 0 回（グラフは取り込み時に作成） | 人・組織・製品・設備のつながり・経緯 |
| DecisionRAG | LLM 最大 9 回（判定） | 条件・否定・言い換えの判断が要る事実の質問 |
| 文書要約（RAPTOR） | LLM 0 回（要約は取り込み時に作成） | 文書の要点・全体像 |
| コミュニティ要約 | LLM 最大 5 回（初回だけ。以後は保存分） | 資料群全体の傾向・テーマ |
| マルチクエリ | 埋め込み（比べる対象ごと） | 比較の質問（比較のときだけ動く） |
| 質問ルーター（補助） | LLM 1 回 | 会話の流れを踏まえた質問の補完（OFF なら規則で判定） |
| 根拠チェック CRAG（補助） | LLM 1 回 | 資料が足りないときの再検索 |
| 再順位付け（補助） | LLM 1 回 | 精度を上げたいとき |

選んだ方式の結果は RRF で 1 つの順位にまとめ、回答は 1 回だけ生成する。回答には「検索方式」と実際に使った
RAG が表示され、出典にマウスを載せると方式ごとの順位・スコアが出る。どの組み合わせがよいかは、
[RAG Orchestrator](../rag-orchestrator/) の「組み合わせ RAG」エンジンで、同じコーパス・同じ質問のまま
単独の方式と比べられる。

## 読み込み結果（どの LLM で読み込んだか）

要約・ナレッジグラフ・埋め込みは、**作った LLM（接続先・モデル・方式）ごとに「読み込み結果」として残す**。
LLM を替えて読み込み直しても前の結果は消えず、文書ごとに使う結果を選べる。

- 文書一覧の「インデックス」の列に、使っている結果の LLM（🤖 qwen3:14b など）と、ほかに残っている結果の数を出す
- 「情報」を開くと、段階ごとに結果の一覧（LLM・状態・エンティティ数・チャンクの完了数・日時）が出る。
  「これを使う」で切り替え、「削除」で消す（使用中を消すと、残りの新しい結果に切り替わる）
- 「別の LLM・方式で読み込む」で、LLM（社外秘の文書はローカルだけ）・モデル名（同じサーバの別モデル）・
  グラフの作り方を選んで読み込む。読み込みが終わるまでは今の結果を使い、終わったら新しい結果に切り替わる
- 埋め込みは質問も同じモデルで埋め込む必要があるため、検索に使うのは設定中の埋め込みモデルの結果だけ
  （ほかのモデルの結果は残すが使わない旨を表示）
- 同じ原本・同じ設定で抽出し直したとき（チャンクが変わらないとき）は結果を残す。チャンクの文字数を変えるなど
  チャンクが変わったときは、チャンクと対応しなくなるので消す
- 読み込み結果の導入前のデータは「以前の取り込み（ローカル LLM・モデル名の記録なし）」として残る

## LLM の使い分け（社外秘はローカル、公開資料はクラウド可）

接続先は2系統を登録する。

- **ローカル LLM**: 社外秘文書を送ってよい接続先（Ollama / LM Studio / vLLM / 社内 Azure OpenAI など）
- **クラウド LLM**: 公開文書だけを扱う接続先（Claude / OpenAI / Gemini / Azure OpenAI）

文書には取り込み時に**区分（社外秘 / 公開）**を付ける（既定は社外秘）。

| 処理 | 社外秘の文書 | 公開の文書 |
|---|---|---|
| グラフ抽出・要約 | ローカル LLM | クラウド LLM（設定でローカルにも変更可） |
| 埋め込み | ローカルの埋め込みモデル | クラウドの埋め込みモデル（未設定ならローカル） |
| 回答 | 根拠に社外秘を1件でも含めばローカル LLM | 公開資料だけならクラウド LLM（自動モード） |

**社外秘のデータをクラウドへ送る呼び出しは、プログラム側で必ず止まる**（`PolicyError`）。設定を誤っても漏れない。
テスト（`tests/test_api.py`）では、モック LLM への全送信を記録して、クラウド側のモデルに社外秘の本文が
一度も届いていないことを確認している。

相談のモード:

- **自動**（既定）: 社外秘資料を根拠に含む回答はローカル、公開資料だけならクラウドで回答。
  補助処理（質問の分析・根拠チェック）はローカル優先。社外秘を参照した相談は以後ずっとローカルで処理する
- **ローカルのみ**: 質問文も含めて外部に送らない
- **クラウド**: 社外秘文書を検索対象から外し、公開文書だけでクラウドが回答する

## 採用した RAG 手法と、この用途に合う理由

文書管理の相談では「特定の数値や手順を聞く」「人・組織・設備のつながりを聞く」「資料全体をまとめさせる」
「比べさせる」が混在する。1つの手法ですべてに強いものは無いため、取り込み時に複数の索引を作り、
**質問ごとに手法を選ぶ**構成にした（2026 年時点の実務での主流もこの「ルーター＋ハイブリッド」構成）。

```
取り込み: 抽出（ページ・スライド・シート・見出し単位）→ チャンク → 全文索引（BM25）→ 埋め込み
          → 文書要約 → ナレッジグラフ（エンティティ・関係・上位概念キーワード）
相談:     質問ルーター → 戦略別の検索（DecisionRAG / Hybrid / グラフ / 要約）→ 根拠の十分性チェック
          （不足なら再検索）→（再順位付け）→ 出典付き回答
```

### 取り込みの順番（遅いローカル LLM でも、取り込んだ文書はすぐ使える）

取り込みは2本のワーカーで進める。

1. **抽出ワーカー**: 届いた文書から順に、テキスト抽出・チャンク分割・全文索引までを行う。LLM を使わないので
   すぐ終わり、文書は「検索可」になって、全文検索・相談に使える
2. **後処理ワーカー**: LLM を使う段階を、文書をまたいで **全文書の埋め込み → 全文書の要約 → 全文書のグラフ抽出**
   の順に進める（検索に効くもの・軽いものから）。グラフ抽出はチャンクごとに LLM を呼ぶので最も時間がかかる

文書一覧の「状態」の下に、処理中の段階（例: グラフ抽出 3/40）か「順番待ち（文書要約・グラフ抽出）」が出る。
画面右上の「取り込み中 N 件」にマウスを載せると、段階ごとの待ち件数が出る。

以前は1本のワーカーが1文書ずつ最後まで処理していたため、ローカル LLM のグラフ抽出が続く間、後ろの文書は
抽出すらされず「待機中」のままで、相談の検索対象にも入らなかった（2026-11-06 に修正）。

ローカル LLM が遅いとき（1回に数十秒かかるとき）は、設定タブの「グラフの作り方」を **高速** か
**語の共起（LLM なし）** にすると、グラフが早くできる（下の表）。「グラフ抽出の上限（チャンク/文書）」を
小さくする・グラフ抽出を OFF にする手もある。全文検索・埋め込み・要約・DecisionRAG はグラフが無くても使える。

| グラフの作り方 | 取り込み時の LLM | 速さ | できるもの |
|---|---|---|---|
| 標準 | チャンクごとに 1 回（エンティティ・関係・説明を書く長い出力） | 遅い | 関係の意味（「製造する」など）と説明つきのグラフ |
| 高速 | チャンクごとに 1 回（名前・種別と関係の組だけ。説明なし） | 出力が数分の1 | 標準に近い形のグラフ。説明は無い |
| 語の共起（LLM なし） | 0 回（一瞬） | 最速 | 本文の語（漢字・カタカナの連なり・型番）と、同じ文に出る語のつながり（LazyGraphRAG の名詞句グラフの考え方）。関係の種類は分からないが、質問の語から PageRank でたどる検索とコミュニティは使える。LLM 未設定でも作れる |

コミュニティ（関連の強いエンティティのまとまり）の要約は、どの方式でも取り込み時には作らず、質問で必要になった
分だけ作る（LazyGraphRAG 方式）。エンティティごとの要約も作らない。文書ごとに別の方式でも作れ、
回答の「使った RAG」の GraphRAG にマウスを載せると、相談先の文書のグラフがどの方式・どの LLM で作られたかが出る。

### グラフ抽出が途中で終わってしまう問題（2026-11-09 に修正）

ローカル LLM で、32KB 程度の文書でもグラフ抽出が最後まで終わらないことが多かった。偽の LLM で再現すると、
**LLM の呼び出しが1回失敗しただけで、その文書のグラフ抽出全体を止めていた**（24 チャンクの文書で 2 チャンク分しか
グラフにならず、しかも文書は「グラフあり」と表示されていた）。失敗の典型は次の3つ:

- 相談の回答中は同じローカル LLM が順番待ちになり、取り込み側の呼び出しがタイムアウトする
- モデルのプロセスが落ちて HTTP 500 が返る（メモリ不足など）
- 受信の途中で止まる・切れる（このときは内部エラーになり、グラフの表示も消えていた）

さらに、アプリを終了・再起動するとグラフ抽出を最初からやり直していた。直した内容:

| 対策 | 内容 |
|---|---|
| チャンク単位でやり直す | タイムアウト・接続断・HTTP 5xx / 429 は、5 秒・20 秒・60 秒と間隔を空け、待ち時間も 2 倍・3 倍に延ばして同じチャンクを最大 3 回やり直す |
| 失敗したチャンクは飛ばして続ける | その依頼だけの失敗（HTTP 400 など）・JSON を取り出せなかったチャンクは記録して次へ進む。設定の誤り（認証・モデル名）だけは止めて理由を出す |
| 受信の途中で切れたら | それまでに受け取った分から JSON を取り出せればそれを使い、無理ならやり直す |
| 一時停止と自動再開 | 接続できない状態が 3 チャンク続いたら一時停止し、5 分後に自動で続きから再開（3 回まで。以後は「続きから再開」ボタン） |
| 続きから進む | チャンクごとの結果を DB に残し、再起動・一時停止の後は済んだチャンクを飛ばす。「失敗したチャンクをやり直す」ボタンもある |
| 相談との譲り合い | 相談の回答を生成している間は、グラフ抽出が次のチャンクを送るのを待つ（最大 4 分） |
| 記録 | 文書の「情報」→「チャンクごとの記録」で、各チャンクの結果・エンティティ数・秒数・試行回数・失敗の理由を見られる。コンソールにも出す |

それでも失敗が多いときは、「チャンクごとの記録」の理由を見る。「思考だけで上限に達し」→ Max Tokens を増やすか
思考の短いモデルに、「繰り返しに入った」「文章が返った」→ JSON 出力の得意なモデル（Qwen2.5 / Qwen3 の Instruct 等）か
「高速」に、「タイムアウト」が多い → 設定の Timeout を延ばす。Ollama は既定の文脈長が短いため、長いチャンクでは
環境変数 `OLLAMA_CONTEXT_LENGTH=8192` 以上で起動すると安定する。

グラフ抽出・要約など JSON を書かせる呼び出しは、ローカル LLM が上限まで止まらないことへの対策をしている
（rag-orchestrator と同じ）:

- ストリーミングで受け取り、JSON が閉じたら・同じ内容の繰り返しに入ったら打ち切る
- Qwen3 系は `/no_think` で思考を止める（取り込みの呼び出しすべて。相談の回答では止めない）
- 上限で切れた JSON からは書けた要素までを取り出し、取り出せなかったときは理由を文書の警告に出す
  （思考で上限に達した・繰り返しに入った・文章が返った）
- やり直しは理由に応じて1回だけ（上限で切れたものは繰り返さない）。以前は温度 0 の同じ呼び出しを繰り返し、
  上限で切れる出力に時間が倍かかっていた
- 処理中は文書一覧に「グラフ抽出 3/40（受信 1,234 字・12 秒）」のように受信の様子を出す

| 手法 | どこで使うか | 選んだ理由 |
|---|---|---|
| 構造を保ったチャンク分割＋文脈ヘッダ（Anthropic の Contextual Retrieval の軽量版） | 取り込み | PDF はページ、PPT はスライド、Excel はシートと行範囲、Word は見出しで分け、各チャンクに「文書名 > 見出し」を付けて索引化。出典をページ・スライド単位で示せる |
| **DecisionRAG**（検索器を使わず、文書の階層を判定モデルでたどる。下の節を参照） | 事実・比較の質問 | 文書管理はフォルダ・文書・見出し・ページという階層を元から持つため、論文の「コーパスの構造をたどる」方式がそのまま使える。字句や埋め込みの近さでは拾えない言い換え・否定・条件を、判定モデルが候補を見比べて判断する |
| Hybrid 検索（BM25 + 埋め込み、RRF で融合） | 事実の質問・全般 | 型番・社内用語は字句一致（BM25）、言い換えは埋め込みが強い。日本語は形態素解析なしの文字バイグラムで扱う |
| GraphRAG / LightRAG 方式のグラフ抽出（**文書単位で増分更新**） | 取り込み | 文書が増え続ける用途なので、全体の作り直しが要らない LightRAG の増分更新の考え方を採用。関係の端点が抜ける LLM の癖は自動補完 |
| HippoRAG 2 の Personalized PageRank | 関係・経緯の質問 | 質問に出る対象を起点にグラフ上で関連度を広げ、2〜3段先の関係（A社→製品→工場）に関わる箇所も拾う |
| LazyGraphRAG 方式のコミュニティ要約（**質問時に必要な分だけ要約**） | 全体の要約・傾向 | 本家 GraphRAG は取り込み時に全コミュニティを要約するため費用が大きい。関連するテーマだけ質問時に要約してキャッシュする |
| RAPTOR 方式の文書要約（部分要約 → 全体要約の2層） | 要約・横断の質問 | 「この資料の要点」「資料全体の傾向」に、チャンクの断片ではなく文書単位の要約で答える |
| 質問ルーター（Adaptive-RAG。検索要否の判定は D2-RAG 等と同じ発想） | 相談の入口 | 質問の種類で検索方法を選び、挨拶・言い換え依頼では検索しない（無関係な資料の混入を防ぐ）。会話履歴から「それ」「この資料」を補った単独の質問に書き換える |
| マルチクエリ（RAG-Fusion） | 比較の質問 | 比較対象ごとに検索して融合し、片方の資料だけに偏らないようにする |
| CRAG（Corrective RAG） | 事実・関係・比較 | 取得した資料で答えられるかを LLM が判定し、不足なら書き換えた検索文で1回だけ再検索 |
| LLM による再順位付け（任意） | 全般 | 精度は上がるが LLM 呼び出しが増えるため既定は OFF |

使わなかったもの: 本家 GraphRAG の取り込み時の全コミュニティ要約（費用）、Self-RAG（専用学習モデルが必要）、
ColBERT 等の専用検索モデル（依存が重い）。比較・評価は [RAG Orchestrator](../rag-orchestrator/) で行える。
## DecisionRAG（検索器を使わない階層ナビゲーション）

Wan, Jünger, Du, Liu, Krishnan, Weinberger（Cornell University / ASAPP）
"Retriever-Free Retrieval: Navigating Documents with Decision Models"
（[arXiv:2610.35868](https://arxiv.org/abs/2610.35868)、2026-10-26）の方式を実装した。

- **考え方**: 第1段の検索器（BM25 / 埋め込み）を使わず、図書館で棚を順にたどるように、
  コーパスの階層を上から下へ判定モデルでたどる。各段では候補を**同じ文脈に並べて一度に**判定させる
  （候補どうしを見比べるので、関連度の尺度がそろう）。上位の枝だけを残して下の段へ進む
- **論文の結果**（著者報告）: 課題向けの学習なし・第1段の検索器なしで、密ベクトル検索＋8B リランカーを
  MultiDoc2Dial で R@1 +13.8 ポイント、Natural Questions で Hit@1 +17.4 ポイント上回った。
  1質問あたりの検索時間は中央値 0.7〜1.8 秒
- **判定モデル**: 論文は TypeSafe の判定専用モデル **Jev**（テキストを生成せず、yes/no の確率や
  選択肢ごとの確率を返す）を学習なしで使っている。公開コードは無い。同じ種類の判定専用 API は
  OpenAI（Decisions API・`gpt-6-luna`）と Azure OpenAI にもある

### この実装

| 論文の要素 | Doc Vault での実装 |
|---|---|
| コーパスの階層 | フォルダ → 文書 → 節（見出しのまとまり。見出しが無い PDF は数ページずつ）→ 段落（チャンク）。子が 24 を超えるノードは、埋め込みがあれば k-means（論文も NQ では埋め込み＋k-means で階層を作っている）、無ければ並び順で中間ノードに分ける。子が1つだけのフォルダは飛ばす |
| ノードの説明文 | フォルダ: 名前・配下の文書名・主なキーワード ／ 文書: タイトル・文書要約・キーワード（要約が無ければ見出しと冒頭）／ 節: 見出し・ページ範囲・冒頭 ／ 段落: 本文 |
| 各段の二値判定（共有文脈・1回で全候補） | **判定 API**: 候補一覧を共有の文脈（Jev は `state`、OpenAI / Azure は `input`）に入れ、候補ごとの「関連する確率」（Jev は `noul`、OpenAI / Azure は `predicate`）を1リクエストで求める（最大 50 件ずつ）。**LLM**: ローカル / クラウドの LLM に候補を並べて 0〜9 で採点させ、logprobs が取れる接続先（OpenAI 互換・Azure）では採点の数字の確率分布から期待値を求める（≒ 確率）。Claude など logprobs の無い接続先は出力された数字を使う |
| ビームサーチ | 各枝に**経路スコア**（根からの経路上の確率の幾何平均）を持たせ、判定済みでまだ展開していない枝の中から経路スコアの上位 k 本（**ビーム幅。既定 4**）を展開する。親の確信度が子の順位に効き、展開した先が振るわなければ前の段の次点へ自動で戻る（バックトラック）。自分の確率が 0.1 未満の枝は展開せず、見つかった上位の段落を上回れない枝しか残らなければ打ち切る |
| ビーム幅の指定 | 設定タブ（既定値）と、相談ごとの「幅」欄（空なら設定の値）。API では `decision_beam` |
| 判定回数の上限 | 上限に収まらない段は、経路スコアの高い親の子から判定し、判定できなかった件数を「検索の流れ」に表示する（黙って捨てない） |
| 段落の選び方 | 閾値で切らず経路スコア順に上位を返す（固い閾値は正解を黙って落とすという、公開実装の検証で繰り返し出た教訓に従う） |
| 選択式の並べ替え（multiple-choice） | 上位 20 件までを「どれが最も答えを含むか」の選択式で比べ、その確率で並べ替える。判定 API は `choice` 質問、LLM は記号 A〜T の1文字を答えさせてその確率を読む |
| 判定回数の既定 | 1質問あたり 8 回（設定で変更可） |
| 新しい文書の追加 | フォルダの位置に入るだけ。再学習・全体の作り直しは不要 |

使い方:

- 相談ごとに「検索」で **自動 / DecisionRAG / 従来型** を選ぶ。
  - 自動: 事実・比較の質問で DecisionRAG と Hybrid 検索を融合する（論文も補完として密ベクトル検索の併用を挙げている）
  - DecisionRAG: 論文どおり第1段の検索器を使わない
  - 従来型: 使わない
- 相談ごとに「幅」でビーム幅（各段で残す枝の数）を指定できる。空なら設定の値（既定 4）
- 回答の「検索の流れ」に、展開した枝ごとの確率と経路スコア、前の段へ戻った回数、判定できなかった件数が表示される
- 設定タブ → RAG の設定 → DecisionRAG で、判定モデル（LLM / 判定 API）・各段で残す枝の数・判定回数の上限・
  選択式の並べ替えを変えられる

### 判定 API（任意）

判定モデルを「判定 API」にすると、テキストを生成せず確率で答える判定専用のモデルで判定する（論文の設定に近い）。
「判定 API の接続」で接続先を選び、API キーなどを入れて「接続テスト」を押す（架空の候補 2 件で 1 回判定する）。

| 接続先 | 送り先 | 認証 | モデル | 入力するもの |
|---|---|---|---|---|
| OpenAI | `https://api.openai.com/v1/decisions` | `Authorization: Bearer` | `gpt-6-luna`（既定） | API キー |
| Azure OpenAI | `https://<リソース名>.openai.azure.com/openai/v1/decisions`（API バージョンを入れると `/openai/decisions?api-version=…`） | `api-key` ヘッダー | デプロイ名 | エンドポイント（リソースの URL）・API キー・デプロイ名 |
| Jev（OpenRouter） | `https://openrouter.ai/api/alpha/decisions` | `Authorization: Bearer` | `typesafe/jev-1.14`（既定） | OpenRouter の API キー |

- 要求と応答の形は、OpenAI / Azure は公式 Python SDK（openai 3.46 の `DecisionCreateParams` / `Decision`、
  Azure の送り先は `AzureOpenAI` クライアント）に合わせ、SDK に同じ要求を作らせて一致を確かめている。
  Jev は公開実装に合わせた
- エンドポイントに `/decisions` まで含む URL を入れた場合は、そのまま使う（API ゲートウェイ経由など）
- 接続先ごとに API キー・プロキシを別々に持ち、切り替えても他の接続先の設定は残る。以前の「Jev の接続」の設定は
  自動で「Jev（OpenRouter）」に移る
- OpenAI / Azure は質問ごとに回答を断る（refusal）ことがある。断られた候補は「関連なし」として扱い、件数を警告に出す。
  すべて断られた段は判定の失敗として扱う（自動モードでは Hybrid 検索で補う）
- 費用の目安: OpenRouter は `usage.cost`（米ドル）、OpenAI / Azure は入力トークン数を「検索の流れ」に表示する
  （OpenAI は出力が課金されない）

**送ってよい文書の区別**: 判定 API は外部サービスなので、**候補がすべて公開文書の段だけ**を判定 API で判定し、
社外秘を1件でも含む段・「ローカルのみ」の相談・社外秘に触れた相談はローカル LLM で判定する（プログラム側で強制し、
テストで送信内容を検査している）。例外は Azure OpenAI で「社外秘の候補も送ってよい」を ON にしたときだけで、
社内で社外秘の扱いが認められた自社のテナントを想定している（ローカル LLM と同じ扱いになる。既定は OFF）。

違いと注意:

- LLM で判定する場合は、論文のように「1回の計算で全候補の確率を読む」のではなく、候補ごとに1桁の数字を
  出力させて読む近似。判定 API より遅く、ローカル LLM では1段に数秒〜数十秒かかる
- 精度はノードの説明文に左右される（論文も限界として挙げている）。文書要約を作っておくと文書段の判定が良くなる
- 前の段の次点へ戻れるのは判定済みの枝だけで、判定回数の上限に達すれば打ち切る。
  自動モードでは Hybrid 検索との融合で取りこぼしを補う
- 判定 API（Jev・OpenAI・Azure）の日本語の文書での精度は未確認。Jev は英語が最も得意とされる。
  OpenAI の選択式（choice）は、確率が最上位の選択肢に寄りすぎるという利用者の報告がある（公式の評価ではない）

## 音声入力（相談の文字起こし）

相談の質問欄の横の 🎤 を押して話し、もう一度押すと文字起こしが質問欄に入る（Esc で取り消し。送信前に直せる）。
音声には質問の内容（社外秘の話も含みうる）が入るため、**社内・ローカルの文字起こしを既定**にしている。

| 方式（設定タブ → 音声入力） | 音声の行き先 | 備考 |
|---|---|---|
| Whisper 互換 API（置き場所: ローカル・社内） | 社内のサーバ・自分の PC | faster-whisper-server（speaches）・LocalAI・vLLM の `…/v1`、whisper.cpp の server の `…/inference`、社内の Azure OpenAI。ブラウザで録音した音声を 16kHz の WAV にして Doc Vault 経由で送る |
| ブラウザの音声認識（端末内） | 外へ出ない | Chrome の「端末内だけで認識」（`processLocally`）に対応したブラウザのとき。言語パックが無い PC では開始時にエラーになり、案内を出す |
| Whisper（置き場所: クラウド）・ブラウザの音声認識（クラウド） | OpenAI / Google / Microsoft など | 「音声をクラウドへ送ってよい」を ON にしたときだけ使う（既定 OFF） |

方式「自動」は、Whisper が設定済みならそれ、無ければブラウザの端末内の音声認識を使う。マイクは
`http://127.0.0.1` か HTTPS で開いたときだけ使える（LAN で共有して http で開いた PC では使えない）。
「接続テスト」は 1 秒のテスト音を送って応答を確かめる。

## 接続設定の例

「設定」タブのプリセットボタンで入力欄が埋まる。

| 用途 | 種類 | Base URL | モデルの例 |
|---|---|---|---|
| ローカル（Ollama） | OpenAI 互換 | `http://127.0.0.1:11434/v1` | `qwen3:14b`、埋め込み `bge-m3`（日本語に強い） |
| ローカル（LM Studio） | OpenAI 互換 | `http://127.0.0.1:1234/v1` | 読み込んだモデル名 |
| クラウド（Claude） | Anthropic | 空（既定） | `claude-opus-5-5`（取り込み用に別モデルも指定可） |
| クラウド（OpenAI） | OpenAI 互換 | `https://api.openai.com/v1` | 埋め込み `text-embedding-3-small` |
| Azure OpenAI | Azure | `https://<リソース名>.openai.azure.com` | デプロイ名 |

- Claude は公式 SDK（`pip install anthropic`）で呼ぶ。API キーは設定画面か環境変数 `ANTHROPIC_API_KEY`
  （SDK の認証プロファイル・`ANTHROPIC_AUTH_TOKEN` でも可）。**認証情報が無い Claude は「未設定」扱い**で、
  公開文書の取り込みや回答はローカル LLM で行う（初期設定のクラウド側は Claude なので、以前はキーを入れて
  いなくても設定済みと判定し、公開文書のグラフ抽出・要約と回答が Claude に回って失敗していた）。
  安全上の理由で回答を辞退された場合は、サーバ側の自動フォールバック（`fallbacks: "default"`）で別モデルが答える
- Claude には埋め込み API が無い。クラウド側の埋め込みは OpenAI 互換の API を指定するか、空欄にする
  （空欄でも全文検索とグラフで検索できる）
- 推論モデル（Qwen3 / DeepSeek-R1 系）の `<think>…</think>` は回答から取り除く
- プロキシは接続先ごとに設定する（設定タブ → 各 LLM の「詳細設定」、判定 API は「判定 API の接続」の接続先ごと）。
  下の「プロキシ」を参照

設定は `doc-vault/docvault.config.json`（API キーを含むため gitignore 済み）に保存される。

### プロキシ

| 設定 | 動き |
|---|---|
| 「プロキシを使う」OFF | 環境変数にプロキシがあっても直結（ローカル LLM の既定） |
| ON・Proxy URL を入力 | そのプロキシを使う（`http://user:pass@proxy:8080` のように認証つきも可） |
| ON・Proxy URL が空 | 環境変数 `HTTPS_PROXY` / `HTTP_PROXY`、無ければ **Windows のシステムのプロキシ設定**（クラウド LLM と判定 API の既定） |

- OpenAI 互換・Azure・埋め込み・判定 API・Claude（公式 SDK）のすべての呼び出しが、この設定どおりの経路を通る。
  記録用のプロキシを2つ（設定用・環境変数用）立てて、実際の SDK（anthropic 2.5）で 31 通りの経路を確認した
- `NO_PROXY` に書いたホストは直結のまま
- 社内プロキシが SSL を検査して社内の CA で証明書を付け替える環境向けに、Claude SDK も OS の証明書ストア
  （Windows の証明書ストア）を信頼する。SDK の既定（certifi だけ）だと証明書エラーになるため
- 自動構成スクリプト（PAC ファイル）には対応していない。PAC を使う環境では、プロキシの URL を直接入力する

```
doc-vault/data/              （--data-dir または環境変数 DOCVAULT_DATA で変更）
  docvault.sqlite3           文書メタデータ・チャンク・埋め込み・グラフ・相談履歴
  files/<文書ID>.<拡張子>     原本
```

## テスト

```bash
cd doc-vault
python -m unittest discover -s tests -v
```

- 実 LLM 不要。`tests/mock_llm.py`（OpenAI 互換・ストリーミング対応の決定論的モック）を使う
- 抽出（DOCX / PPTX / XLSX / PDF / CSV / HTML / MD / 文字コード）、検索部品、設定の検証、
  Claude 呼び出しの形（偽の SDK で検査）、グラフ（端点補完・PPR・コミュニティ・区分の伝播）、
  DecisionRAG（階層の構築と分割・logprobs からの確率・ナビゲーション・判定 API の 3 接続先の要求形式・送り先・
  回答拒否・分割・社外秘の扱い・古い設定と DB の移行）、
  API 統合（取り込み → 検索 → 相談の各モード → グラフ → 編集・削除）、社外秘がクラウドへ送られないことの検証
- `test_ingest_resilience.py`: 失敗の型（HTTP 500・タイムアウト・受信の途中で停止・HTTP 400・設定の誤り・LLM の停止）を
  偽 LLM で起こし、グラフ抽出が最後まで進むこと・一時停止から続きだけを処理すること・再起動後に残りだけを処理すること
- `test_features.py`: 検索方式（速さ優先は LLM を回答の 1 回だけ呼ぶ・選んだ方式だけを使う・既定の方式）、
  読み込み結果（LLM ごとに残る・切り替え・削除・クラウドの拒否・抽出し直しで残る・旧 DB の移行）、
  フォルダ（作成・名前の変更・削除・移動・一括操作・相談先の書き換え）、相談先、採用根拠と使った RAG、
  語の共起グラフ（LLM を呼ばない）、文字起こしの中継（Whisper / whisper.cpp / Azure・クラウドの許可制）
- PDF のテストは pypdf か PyMuPDF があるときだけ実行される

## 構成

```
server.py                 HTTP サーバ（標準ライブラリ）・API・SSE ストリーミング・アクセストークン
docvault/
  config.py               2系統の接続設定・データ取り扱いポリシー・RAG 設定
  llm.py                  OpenAI 互換 / Azure / Claude（公式 SDK）。区分ポリシーの強制・ストリーミング・think 除去
  extract.py              PDF / DOCX / PPTX / XLSX / CSV / HTML / MD / TXT の構造つき抽出
  textutil.py             チャンク分割・トークン化・BM25（転置インデックス）・ベクトル検索・RRF・JSON 抽出
  db.py                   SQLite（文書・チャンク・ベクトル・グラフ・相談）と原本ファイル
  indexer.py              取り込みパイプライン（抽出ワーカーと後処理ワーカー・やり直し・一時停止・続きから再開）
  readings.py             読み込み結果（LLM ごとの要約・グラフ・埋め込みの記録・切り替え・チャンクごとの記録）
  folders.py              フォルダの一覧・作成・名前の変更・削除・文書の移動と、相談先（範囲）の判定・説明
  ragopts.py              検索方式（使う RAG の選択）と、1 問あたりの LLM 呼び出しの目安
  terms.py                LLM を使わない語の共起グラフ（rag-orchestrator と同じ内容）
  speech.py               音声入力の文字起こし（Whisper 互換 API への中継・クラウドは許可制）
  retrieval.py            検索インデックス（BM25 + 埋め込み空間ごと）と Hybrid 検索
  graph.py                グラフ抽出・文書横断グラフ・PPR・コミュニティ・遅延要約
  rag.py                  相談パイプライン（ルーター・戦略別検索・CRAG・再順位付け・回答・出典）
  decision.py             DecisionRAG（階層の構築・共有文脈の判定・ビームでのナビゲーション・選択式の並べ替え）
  decision_api.py         判定 API のクライアント（Jev / OpenAI / Azure OpenAI の Decisions API。公開文書の候補のみ）
  samples.py              サンプル文書と DOCX / XLSX / PPTX / PDF の最小生成器
static/                   画面（index.html / app.js / style.css / graphview.js）
tests/                    ユニット + API 統合（モック LLM）
```

`static/graphview.js` は [RAG Orchestrator](../rag-orchestrator/) と共通のグラフビューア
（同一内容であることをテストで確認している。直すときは両方を揃える）。

## 既知の制約

- スキャン画像の PDF（文字が埋め込まれていないもの）は OCR が必要で、現状は取り込めない（警告を表示）
- 図・グラフ・画像の中身は読まない（テキストと表のみ）
- 埋め込み検索は総当たり（numpy があれば高速化）。目安として数万チャンクまで
- 区分を「公開 → 社外秘」に変えても、それまでにクラウドへ送った内容は取り消せない（以後の処理がローカルになる）
- 実際のローカル LLM・Whisper サーバ・Chrome の端末内音声認識では未確認（偽の LLM・偽の Whisper とブラウザ操作で確認）。
  「高速」「語の共起」で作ったグラフの質（標準との差）も、実データでは測っていない
- 語の共起グラフは形態素解析を使わないため、ひらがなを含む語（「ばらつき」など）は語として拾わない
