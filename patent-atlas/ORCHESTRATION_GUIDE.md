# 統括モード

「統括モード」は、同じ公報・分類選択・検索式履歴を使い、CSVを起点に各機能を1サイクルずつつなぎます。

1. **分類探索**: 対話で探索の公報群と、同じテーマの探索ラボにある公報群を統合します。探索ラボを分析し、分類候補を共有します。
2. **分類の確認**: 既定ではここで止まります。候補の根拠を読み、選択を変更して再開します。確認中は対話で探索の分類操作も利用できます。
3. **特許の判定**: 有効にした場合は、地図の「LLMにおまかせ」と同じサービスで未判定の公報を判定します。手動判定、保存済みの採用・不要判定、保存済みの保留は再判定しません。
4. **学習**: なし・軽量学習・Transformerを選べます。モデル学習にAI判定を含めるかは別指定です。学習の教師データが不足すると、この工程で止まり、ラベル追加後に再開できます。
5. **分類・検索式更新**: ラボを再分析し、共通の分類抽出を使って次の検索式を作成します。FIやFタームから導いた分類候補にも由来を残します。
6. **次の式を確認**: 既定では検索式を保存する前に止まります。分類・追加語・除外語を編集して確認すると、対話で探索の検索式履歴に保存します。必要公報にも出現する語のNOT指定は拒否します。
7. **次のCSV待ち**: 検索先で式を実行し、結果をCSVで追加して再開すると次のサイクルに進みます。再取込せず同じ公報データのままの再開はしません。検索し直したCSVを取り込んだ場合は、結果が同じ公報群でも次のサイクルへ進めます。

確認をオフにすると、分類の追加推奨と検索式保存まで連続実行します。既存選択を自動削除せず、分類のNOTも自動作成しません。分類の追加推奨には確定判定の支持を使い、モデルの予測は別に表示します。取りこぼしの有無や検索結果の件数は検索先で確認してください。

## 停止・再開と保存

- 全タブ共通の1つのジョブで動作し、学習・判断エージェント・探索ラボの処理と二重起動しません。
- LLM判定は検証済みのバッチを保存します。停止要求中の未保存の応答は破棄し、保存済み判定を保持します。通信応答待ちの停止には時間がかかる場合があります。
- アプリを閉じた場合は中断として復旧し、利用者が再開するまでネットワーク要求を再送しません。判定済み公報は再利用します。
- 確認中はラベルの編集ができます。途中でテーマ・本文・公報群を変更すると、古い確認内容で処理を続けないよう再開を拒否します。CSVの追加は「次のCSV待ち」で行ってください。
- 確認待ち中に他タブで新しく選んだ分類は、古い確認画面に表示されていなくても続行時に保持します。確認画面に当初から選択済みだった分類は、チェックを外して解除できます。
- 「工程をリセット」は公報、判定、分類選択、検索式を保持し、統括モードの工程だけを初期化します。
- 学習工程で停止した場合は、学習方式とAI判定の利用だけを変更して再開できます。「学習なし」に変更すると、保存済み判定から検索式の更新へ進みます。
- 判断基準を変えて新しく開始しても、保存済み判定は自動で上書きしません。再評価する公報は地図で判定を解除してから実行してください。
- 1サイクルの判定上限は1〜5000件です。上限で未処理が残った場合も件数を表示します。再度判定したい場合は工程をリセットし、同じCSVから新しいサイクルを開始できます。

## API

`POST /api/orchestration/start`

```json
{"criteria":"対象技術を判断する基準","judge":true,"learning":"none","include_agent":false,"max_items":5000,"threshold":0.8,"review":true}
```

`POST /api/orchestration/resume` は、確認中なら `selected_keys`、検索式確認中なら `include_terms` と `exclude_terms` も受け取ります。キーは `IPC:H01M10/0562`、`F-term:5H029AJ01` のように分類体系を含めます。未指定なら提示された案を使います。

`paused` または `error` で `stage` が `train` の場合だけ、`learning` と `include_agent` も変更できます。判断基準など他の設定はそのサイクルの設定を継続します。

`POST /api/orchestration/stop` は停止要求、`POST /api/orchestration/reset` は実行中以外で工程をリセットします。

状態は `GET /api/state` の `orchestration` で取得します。`status` は `idle` / `running` / `review` / `paused` / `error` / `waiting_csv`、`steps` は工程表示、`checkpoint` は編集する案、`summary` は判定数と保存した式、`logs` は工程ログです。

このCSV運用では外部特許の自動検索を行いません。LLMの接続設定とプロキシは設定タブの共通設定を利用します。Local LLMのモデル学習を行う機能ではなく、LLMによる判定と任意の分類器学習を別工程として実行します。

## 収束グラフと保留の確認

統括ワークフローの「探索は、落ち着いてきた？」で検索回ごとの変化を表示します。横軸は記録した検索回、縦軸は変化率です。学習損失やモデル精度のグラフではありません。

- **新しい必要特許の割合**：今回必要と判定した公報のうち、それ以前の記録で必要として現れていなかった公報の割合。
- **IPC構成の変化**：必要公報のIPCサブクラス分布と前回分布の距離（全変動距離）。複数IPCを持つ公報の重みは合計1とします。本文の意味を直接比較する指標ではありません。
- **検索総件数の変化**：前回との総件数差の絶対値を、両回の大きい総件数で割った値。
- **検索規模**：今回のCSVの重複を除いた公報数と、利用者が入力した検索サイトの総件数。累積の地図の件数とは別です。

最初の記録の変化率、未入力の総件数、比較できないIPC構成は空欄です。過去の検索式だけから結果を推定してグラフを作ることはしません。

CSV取込時に、そのCSVに含まれた公報番号と検索式の初期候補を保存します。「今回の検索結果を記録」で実際に使った式と検索サイトの総件数を確認して保存してください。統括モードで式を保存したときにも、取込済みの最新CSVを自動記録します。記録の検索式は取込時の式に紐付き、これから検索する次の式には紐付けません。同じCSVの再記録は最新の1点の更新となり、検索回は増えません。

更新前からある特許群は、必要なら作業領域の基準点として記録できます。その時点では検索回との対応がないので、収束完了の根拠にはしません。新しいCSVから比較可能な履歴が始まります。工程リセットと再起動で記録は保持され、テーマ変更後の記録開始時には以前の履歴をプロジェクト内へ退避します。

安定の目安は、3つの変化率が各5%以下・新規IPCサブクラスなしの比較が3回連続することです。最短でも4回の検索結果が必要です。両回のCSVが総件数分あり、必要公報すべてに明示されたIPCサブクラスがあり、保留・未判定が解消されていることも確認します。FI・Fタームから推定したIPCは、この分布へ自動算入しません。同じ検索サイト・対象期間・公報単位で比較してください。これらは探索を終える目安で、検索漏れがないことの保証ではありません。

「保留を、人の目で確認。」では要約・IPC・LLMの理由と自己評価を読み、必要または不要を確定します。次の保留へ移るだけでは判定を変更しません。確定は共通の人の判定として保存され、次の検索式を更新するときの根拠になります。保存済みの検索式を直接書き換える操作ではありません。最新回を記録済みなら、その回のグラフも更新します。地図など別の場所で判定を変えた場合は「この回の判定を更新」で反映します。

完了条件を満たすと「確認して探索を完了」が使えます。自動では完了しません。新しいCSVや判定の変更があると、再び記録・確認が必要になります。

- `POST /api/convergence/record`: `total_hits`（不明ならnull）、`query_id`（参考記録ならnull）、`observation_id`（最新CSV ID、基準点はnull）。
- `POST /api/convergence/review`: `id`、`label`（keep / exclude）、任意の `expected_reason` / `expected_confidence`。現在保留の公報だけを確定します。
- `POST /api/convergence/complete`: 最新のデータで条件を検証して人の完了を保存します。
- `GET /api/state` の `convergence` は公開指標、`search_result` は最新CSVの情報です。プロジェクト書出しには公報番号付きの観測記録も保存します。
