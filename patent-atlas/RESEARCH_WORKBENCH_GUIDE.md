# 調査ナビの使い方

初期画面は4つの入口です。既存のDB出力形式、LLM、プロキシ、分類辞書、表示設定を共用します。個別機能は「04 個別の機能を使う」から開けます。

## 01 ターゲットから作る

調査目的・説明・KWを入力し、取り込んだ特許を最大20件選びます。CSVの追加、または公報番号・名称・要約・分類の手入力にも対応します。公報番号だけでの自動取得ではありません。

「LLMで観点・広げ方を起案」は、選択した特許の名称・要約・分類を既存のLLMへ送ります。実付与IPC/CPC/Fターム、FIからのIPC候補、Fタームのテーマ対応範囲、上位分類、語句に基づく仮説を分けて表示します。FIを独立した検索フィールドとして新設したものではありません。FIの原文は保持し、確認可能なIPC部分・対応範囲を利用します。

「入力をそのまま整理」は通信せず入力を整理します。入力語を増やさず、あらかじめ定義した少数の探索軸に一致する語だけ、仮のORグループを提案します。未知の語の意味分析、同義語生成や概念の抽象化は行いません。説明文だけの場合はLLM起案またはKW・観点の入力を使ってください。

Local LLMの生成が遅い場合は「表示・接続設定」の「LLM応答の待ち時間」を調整できます。既定120秒、設定範囲30〜600秒です。時間超過では前の計画を保持します。入力を短くする方法も使えます。モデルや接続先は自動で変更しません。

観点は任意の別窓で入力できます。1行に1件、最大8件。必要に応じて `必須:`、`任意:`、`除外:` を付けます。LLM起案後は採用する観点をチェックし、各語とORグループを編集できます。抽象語は追加ボタンを押したものだけが条件に入ります。同じ観点の語と同じORグループの観点は和集合（OR）、独立したグループ同士は積集合（AND）、除外観点はNOTです。分類も任意に選択し、選ぶと分類OR群をANDで加えます。

### 和集合・積集合の使い分け

同じ対象を探す言い換えや代替表現はOR、独立して必要な構成・工程・課題はANDで組み合わせます。一般語か専門語かだけでは決めません。例えばKWが「自動運転 自動車 運転システム」なら、初期案は **自動車 AND（自動運転 OR 運転システム）** です。「自動運転」と「運転システム」の両方を記載した文献だけに絞ることを避けます。

| 文献で確認できる語 | このKW条件への一致 |
|---|---|
| 自動車・自動運転 | 一致する |
| 自動車・運転システム | 一致する |
| 自動車のみ | 一致しない |
| 自動運転・運転システムのみ | 一致しない |

この表は検索語の論理関係の例で、特許の要否判定ではありません。「運転システム」は「自動運転」より広い代替表現なので、検索後に不要例が増えすぎないか確認してください。

通信なしで提案するのは、自動運転・自律走行・運転システムなどの軸、電池の英日表記、固体電解質の英日表記という3つの小さな語群だけです。全技術分野を理解する辞書ではなく、未知語を無根拠にまとめません。未知分野では「LLMで観点・広げ方を起案」で意味関係によるグループを提案し、理由を見て手動で変更できます。語の原文は保持し、グループを変えても語自体は削りません。

観点カードで同じORグループを選ぶと和集合、独立条件を選ぶと他グループとの積集合になります。別窓で明示した `必須:` / `required:` 観点は、他観点のORで代替できない独立条件として保護します。接頭辞のない観点は初期状態では独立ですが、グループを変更できます。除外観点は肯定観点のORグループへ入れません。

LLMが同じ語を繰り返した場合は、大文字・小文字の違いを含めて重複を整理します。具体語と抽象語の両方にある語は具体語に残し、確認事項に表示します。異なる意味の語や同義語をまとめる処理ではありません。

LLMが入力観点のIDを返さない場合でも、元の入力観点は先頭に保持します。その理由欄に「利用者の原文」「抽象化は未実施」と表示し、LLMの追加提案と分けます。8観点の上限では入力観点を優先し、省略した追加提案の件数を知らせます。同じIDの名前・役割を勝手に変えた応答や、不正な根拠を含む応答は採用しません。

プレビューで論理構造を確認してから検索式を作成します。ORグループを編集した場合もプレビューし直します。元の入力を変更したら再起案が必要です。今回の更新で過去に保存した検索式は書き換えません。新しいグループ化は新規起案・明示的な適用で利用します。条件を無言で取り落とさないため、8観点に割り当てきれないKWは追加・省略の確認を求めます。ターゲットの参照情報は検索結果と別に保存され、CSVの置換・入口の変更・選択解除後も残るため再選択できます。未選択の参照を自動選択したり検索結果に混ぜたりせず、保存参照は最大5,000件です。

## 02 ターゲットを探す

広いKW検索と仮の分類候補を併用する方式を推奨します。話を観点に分け、まず分類条件なしの式も試します。保存済みの出力先で検索し、CSVを取り込み、代表的な特許を選んで「選んだ特許から作る」へ移ります。

新しいWeb検索APIやDBは追加していません。検索は既存のサービスを開いて行い、CSVで戻す方式です。EPO OPSが既に設定されている場合は「04 → 探索ラボ」で既存の取得機能も使えます。

## 03 過去の式から作る

式のコピペ、TXT・JSONファイルの読込に対応します。J-PlatPatの対応構文とPatent Atlas構造化JSONは論理木として取り込みます。対応構文は `[]`、`*`、`+`、二項の `-`、`/TX`・`/IP`・`/CP`・`/FT`、引用した句です。同じ階層に優先順位が曖昧な演算子が混在する式、その他の検索サービスの生構文は参照用として保存します。完全な汎用パーサーではありません。

今回の目的と適応先の技術を記入し、手動または明示的なLLMボタンで語句・分類の置換案を作ります。理由・NOTの範囲を確認し、プレビュー後に採用します。分類体系や論理構造を勝手に変更しません。これは検索条件の調整で、LLMの重みを学習する処理ではありません。

## マップ・改善・採用

「調査ワークスペース → 特許の地図」でPCA / t-SNE / UMAPを切り替えます。名称・要約の文字TF-IDFを最大64次元へ圧縮した共通表現を使い、各方式で実際に計算します。特許専用Transformer埋め込みではありません。t-SNEとUMAPは4件以上が必要です。UMAPの初回はコンパイルに時間がかかります。

マウスオーバー・キーボードフォーカスで内容を確認できます。選択した点を「追跡に固定」するか、特許リストの「追跡」を押すと、公報ID・色・番号・移動線を保ちます。重なった点はリストから指定できます。静止表示・OSの動きを減らす設定にも従います。

人の必要/不要からS/Nと必要割合を計算し、AIの判定・未確認・保留は分けて表示します。境界候補は高次元の必要/不要の近傍、モデル関連度の中間、LLM保留の別々の理由で提示します。2D上の距離は検索の正解や再現率ではありません。

採用理由とその時点の評価を記録できます。現在のCSVと当該式の対応が不明なら参考評価として明示します。採用記録は探索の完了とは別で、既存の統括・収束グラフを使って反復を続けられます。観点式の改善は論理構造を保持します。取り込んだ任意構造の分類置換は「過去の式から作る」で行い、OR/NOTの位置を保ちます。

LLM判定の基準が空なら、適用済み検索式の目的・観点と論理構造を使います。同じORグループ内は「いずれか」として伝え、すべてを同時必須に戻しません。手入力した判定基準は優先します。未採用の計画を判定基準へ混ぜません。

設計根拠は [プロンプト調査](PROMPT_RESEARCH.md)、整合性の確認は [監査記録](WORKFLOW_AUDIT.md) を参照してください。

## 更新時

通常の依存にUMAPを追加しました。更新後はアプリのPython環境で `python -m pip install -r requirements.txt` を実行してください。既存環境へUMAPだけを追加するには `python -m pip install -r requirements-map.txt` も使えます。設定ファイルやワークスペースの置き換えは不要です。
