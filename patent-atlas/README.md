# Patent Atlas

Python（FastAPI）＋HTML / CSS / JavaScriptで動く、ローカルの特許検索式提案アプリです。`for_eigyo` の独立したアプリとして配布します。本番検証も、利用するPC上で単一ユーザー・1ワークスペース・Python 1プロセスで実行する構成です。

## 起動

Python 3.11以上を用意してください。WindowsのPython 3.13で検証しています。初めて取得する場合は、ターミナルで次を実行します。すでにリポジトリがある場合は、その中の `patent-atlas` フォルダーへ移動してください。

```text
git clone https://github.com/tyama-ds/for_eigyo.git
cd for_eigyo/patent-atlas
```

Windows PowerShellでは、依存パッケージの準備と起動をまとめて実行できます。`-Port` を省略して `./start.ps1` だけでも、既定の8810で起動します。

```powershell
./start.ps1 -Port 8810
```

スクリプト実行が制限される環境では、ポリシーを変更せず次のコマンドを使えます。

```powershell
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt
./.venv/Scripts/python.exe run.py
```

macOS / Linux用の起動手順も用意しています。ただし、これらのOSでの実機検証は未実施です。

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python run.py
```

[アプリを開く](http://127.0.0.1:8810/)。既定ポートは **8810** で、同じリポジトリの llmlab Studio と分けています。変更する場合は `run.py --port 8811` のように指定します。手動起動したターミナルでCtrl+Cを押すと終了します。localhost限定・単一プロセスの設定は維持しており、公開ホスティング用の認証や複数ユーザーのデータ分離は追加していません。

### App Portalから開く

初回の依存パッケージの準備が終われば、[App Portal](../launcher/README.md) の **Patent Atlas** カードから起動できます。登録コマンドの `{app_python}` は、このアプリの `.venv` があればそのPythonを使い、なければポータルを動かしているPythonを使います。後者を利用する場合は、そのPythonにも `requirements.txt` の依存パッケージが必要です。カードを押してもパッケージは自動インストールされません。

Windowsでは、セットアップ後に `.venv/Scripts/pythonw.exe` で `launch.py` を実行して、既定ブラウザーで開くこともできます。こちらもポート8810を使用します。デスクトップショートカットは同梱せず、自動作成もしません。必要ならこのPythonと `launch.py` を参照するショートカットを作成してください。起動ログは `server.out.log` / `server.err.log` です。ブラウザーを閉じても、このランチャーが起動したサーバーはバックグラウンドで動きます。

### データの保存

取得直後は空のワークスペースから始まります。開発時の特許データ、判定履歴、接続先の認証情報は含まれません。保存先は既定でアプリフォルダー内の `data/` です。別の場所に保持する場合は環境変数 `PATENT_ATLAS_DATA`、または `run.py --data-dir <保存先>` を指定します。`--data-dir` の指定を優先します。更新前にサーバーを終了し、この保存先フォルダーをバックアップしてください。`data/` と認証情報はGitへの登録対象にしないでください。

まず右上の「サンプルを試す」を押すと、架空の特許72件を読み込めます。`DEMO-*`は実在する公報番号ではありません。

## 調査ナビから始める

初期画面を「ターゲットから作る」「ターゲットを探す」「過去の式から作る」「個別の機能を使う」の4入口へ整理しました。目的・観点別の検索式、根拠付き分類、過去式の適応、PCA/t-SNE/UMAPとS/Nによる判断に対応します。既存の接続・DB設定は共用します。[操作ガイド](RESEARCH_WORKBENCH_GUIDE.md)、[プロンプトの研究根拠](PROMPT_RESEARCH.md)、[整合性監査](WORKFLOW_AUDIT.md)を参照してください。

更新後はアプリのPython環境で `python -m pip install -r requirements.txt` を実行してください。UMAPを通常の依存へ追加しました。保存済みワークスペース・設定の置き換えは不要です。

「LLM応答の待ち時間」は既定120秒、30〜600秒で調整できます。Local LLMの生成が時間超過になる場合に延長してください。接続自体の待ち時間は10秒です。接続失敗・応答待ち時間超過・JSON形式の問題は分けて表示します。

## 対話で探索

画面はアイボリー・インディゴ・銅色を基調にした紙の地図風のデザインです。上部の「画面の動き」で「動き：自動」「動き：あり」「静止表示」を選べます。動きが有効なときはタブ・ステップの短い切り替えと分類の穏やかな浮遊を表示し、静止表示では止めます。OSの「動きを減らす」設定は常に優先します。表示設定はブラウザーに保存され、検索条件やワークスペースのデータは変更しません。

**個別の機能 → 探索ラボ**では、技術を装置・材料・製造・界面・性能・用途の6観点に分けて探索計画を作成できます。検索結果CSVを繰り返し追加し、公報の分類・ファミリー・手動判定から候補と次の検索案を更新します。辞書による仮説と公報の根拠を区別し、選んだ分類を手動探索へ引き継げます。CSV分析はAPI不要です。[探索ラボの設計と操作手順](DISCOVERY_GUIDE.md)を参照してください。

**個別の機能 → 統括・収束を見る**では、分類探索 → 特許判定 → 任意の学習 → 分類・検索式更新 → 次のCSV待ちをつなぎます。既定では分類と検索式の確認で止まり、手動修正して続行できます。各モードが同じ公報・判定・接続設定を使い、完了した判定を再利用します。進捗表示、停止・再開、次のCSVの追加に対応しています。[統括モードの操作手順](ORCHESTRATION_GUIDE.md)を参照してください。

**収束グラフと保留の確認**では、新たに記録した検索結果から、新しい必要特許の割合・必要特許のIPC構成の変化・検索総件数の変化を表示します。学習損失を示すグラフではなく、過去の検索結果を推定して埋めることもありません。保留は要約とLLMの理由を読んで人が必要・不要を確定します。比較可能な記録がそろい、3回連続の安定などの条件を満たしたら、人が探索の完了を確認できます。総件数の入力、記録の条件と制限は[収束グラフと保留の確認](ORCHESTRATION_GUIDE.md#収束グラフと保留の確認)を参照してください。

1. **Step 00**：キーワード・分類の直接指定・取込済みターゲット特許から起点を作ります。IPCの上位・下位を「広げる」「狭める」で探索し、クリックまたは自由な線で囲んで選びます。英語の複合語は `"solid electrolyte"` のように囲みます（24語句まで）。キーワードを空欄にすると分類だけの検索式を作成できます。詳しい操作は [分類探索ガイド](CLASSIFICATION_GUIDE.md) を参照してください。
2. **Step 01**：分類とキーワードから検索式を作成。「出力する検索サービス」を選び、形式変換後の式をコピーまたはテキスト保存。検索サイトで検索し、結果CSVをこのアプリへ読み込みます。
3. **Step 02**：タイトル・要約のTF-IDF表現を用い、PCA・t-SNE・UMAPを切り替えて配置します。群の色は従来のK-meansを共用します。点にマウスを重ねると要約、出願人、分類、入力語の一致、配置理由を表示します。点を選択して「必要」「不要」を一括指定し、学習します。
4. **Step 03**：要否と学習後の関連度から特徴語を抽出。追加語・除外語を選び、改善式を作成。前回の条件はチェック済みで引き継ぎ、解除した語は明示します。次のCSVで繰り返します。

同じ探索軸の語はOR（和集合）、独立した条件はAND（積集合）で結びます。調査ナビではグループを手動調整でき、LLMにも意味に応じた組合せを提案させます。オフラインの自動グループ化は既知の3軸に限定します。分類候補はOR、追加語はOR群をANDで結びます。分類未付与の公報や同義語を拾うには、分類条件なしの広い検索も比較してください。元の設計式は参照用として折りたたんで表示し、コピーには選んだサービスの構文を使います。

除外候補は既知の必要文書に出現しない語に限定し、選択した語だけNOTにします。これで未発見の必要特許の除外まで防げるわけではありません。追加語を選ぶと、その追加条件で既知の必要文書が何件残るかを表示します。

### 検索サービス別の出力

| 出力先 | 貼り付け先 | このアプリで出力できる分類 |
|---|---|---|
| J-PlatPat | 特許・実用新案検索 → 論理式入力 | IPC / CPC / F-term |
| Derwent Patent Search / Innovation | Expert Search | IPC / CPC / F-term |
| Derwent Innovations Index | Web of ScienceのAdvanced Search | IPC |
| Espacenet（EPO / 欧州） | Smart search | IPC / CPC |
| USPTO Patent Public Search（米国） | Advanced Search | IPC / CPC |
| WIPO PATENTSCOPE | Advanced Search | IPC / CPC |
| Google Patents | Advanced SearchのSearch Terms | CPC |

「EUpatent」はEspacenet、「USpatent」はUSPTO Patent Public Searchとして実装しています。Derwentは製品間で構文が異なるため2形式に分けています。

- 日本語検索に対応しない出力先では、式のコピーを保留します。「出力用の語句を編集・英語に置き換える」で各語句を変更してください。自動翻訳は行いません。
- 未対応分類を勝手に削除しません。必要な場合だけ「未対応分類を今回の出力だけから外す」を選択してください。OR群から一部を外すと絞り込みが強まり、分類群をすべて外すと範囲が広がります。
- IPCとCPCは同じ記号でも別の分類として保持します。未確認分類は確認したうえで利用する指定が必要です。
- IPCの上位分類（セクション・クラス・サブクラス）も初案に選択でき、下位分類を含む範囲として出力します。J-PlatPatでは `B/IP`・`B60/IP`・`B60W/IP` のように上位IPCも出力でき、上位という理由だけで保留しません。形式ごとの対応範囲と確認状況は[上位分類の操作と対応範囲](CLASSIFICATION_GUIDE.md)を参照してください。
- 過去の検索式も履歴から同じ出力画面で選択できます。出力用の語句変更・分類の省略は保存済み検索式を変更しません。
- 出力ごとに対象フィールド、言語、下位分類の扱い、貼り付け先、出典を表示します。既定の「DB標準のコード指定」は全サービス共通の完全一致を意味しません。
- Derwent Innovationは2020年の公式公開研修資料に基づきます。契約中の画面でCheck Syntaxを確認してください。DIIはタイトル・要約検索、InnovationのCTBはタイトル・要約・請求項検索で、通常の全文検索とは異なります。
- 公式資料との照合であり、各サービス上での検索実行・ヒット集合の同等性は未検証です。ワイルドカードや任意のBoolean式の取り込みは未対応です。

実装根拠と監査で修正した問題は [AUDIT.md](AUDIT.md) を参照してください。

### CSV

- UTF-8/BOM、Shift-JIS（CP932）、BOM付きUTF-16。区切り文字はカンマ・タブ・セミコロン。
- 上限20MB / 5,000行。必須は発明の名称。要約があると分析しやすくなります。
- 日本語・英語の一般的な列名を自動認識。不明な場合は列の割り当て画面を表示します。
- 公報番号、発明の名称、要約、出願人、IPC、FI、F-term、公開日、ファミリーIDに対応。
- 同一公報番号の重複を除外します。番号がない場合はタイトル＋要約から内部IDを生成します。
- CSV取込時に「追加・判定を保持」と「置き換え」を選べます。統括モードの次のCSVは追加が初期値です。同一公報は既存の本文・判定・スコアを保持し、空欄の分類等を補います。本文が食い違う同一公報は取込を止めます。置き換えは現在の特許群・判定・学習結果を置き換えるため、必要な結果は先にJSON/CSVで書き出してください。
- IPC欄が空でもFI・Fタームを独立して保存し、共通処理でIPC候補を補います。FIからの対応候補、Fタームのテーマ→FI範囲からの広い候補には由来を表示し、公報に実際に付与されたIPCとは区別します。FタームはIPCの単純な下位分類ではありません。
- マップの距離は表現の類似度です。軸に技術的な単位はなく、類似特許の重なりを見やすくする微小な表示ずらしを加えています。
- 検索サイトで「なぜヒットしたか」はCSVから断定できません。表示するのは入力語一致・配置理由です。

## Local LLMのJSON応答

Qwen等の思考モデルでは、`<think>…</think>` を最終回答から分離してJSONを読み取ります。開始タグがチャットテンプレート側にあり、応答に終了タグだけが出る形式にも対応します。`message.content` は文字列と `text` / `output_text` ブロックの配列を扱い、`reasoning_content` / `reasoning` や思考用ブロックの内容を分類候補・判定として採用しません。JSON文字列の値に含まれるタグはそのまま保持します。

思考だけで本文がない場合や `finish_reason: length` の場合は、本文の型エラーではなく、最終回答なし・出力上限として扱い、最大1回だけ再試行します。Local LLMに設定した通常のQwen3では、その再試行時に限りシステム指示へ `/no_think` を付けます。思考専用モデル、Qwen3.5、Instruct/Coder/VL等にはこの切り替え指示を付けません。これは[Qwenの思考モード](https://qwen.readthedocs.io/en/latest/getting_started/quickstart.html)に基づく指示で、サーバー独自のAPIパラメーターは追加しません。元の入力と判定スキーマは保持します。再試行後も本文がない場合は、LM Studio側の思考設定・出力上限を確認してください。[LM Studioの思考フィールドの説明](https://lmstudio.ai/docs/developer/api-changelog)も参照できます。

LLMへのリクエストには最大出力4,096トークンを指定します。コードブロックで囲まれたJSONにも対応し、本文が途中で終わった場合やJSONが不正な場合は、元の依頼を短い出力指定で1回だけ再試行します。途中までの候補を補完して採用することはありません。接続エラー・HTTPエラー・応答形式の不一致は、JSON生成エラーと分けて表示します。

分類提案は最大6件・短い理由を依頼し、名称はアプリの分類辞書で表示します。収録IPC辞書（2026.01）にないLLM提案は自動候補から除外し、画面に説明します。コードの存在確認は技術的な適合性の保証ではありません。エラー時は、それまでの候補・選択・検索式を保持します。

対話で探索の返り値は `candidates: [{kind, code, reason}]` です。「今回のLLM提案」に返却・反映・新規・既存重複・除外の件数と理由を表示し、提案されたコード自体を上位分類と一緒に地図へ出します。「今回のLLM候補を地図で見る」で提案だけに絞れます。同じコードが辞書候補にあってもLLMの理由を保持します。候補への反映だけでは分類の選択・検索式・探索ラボの計画は変わりません。必要な分類を選択してから初案を作成してください。

完成したJSONの候補一覧は1件ずつ検証します。不完全なコード・不正な候補・未確認IPCが混在しても、有効な候補は反映し、除外したコードと理由を表示します。全件が無効なら前の状態を保持します。全半角・空白・Ftermなどの体系名・一致する `IPC:` ラベル・厳密な版注記は表記として正規化しますが、`H04N21` に `/00` を補うなど分類を推測する補正や、複数コード・FI付加記号の切り捨ては行いません。

除外コードの先頭部分から確認できる上位IPCがある場合は、正式名称を別枠に表示し「上位の…を候補に追加」から探索できます。元コードの置換・同等範囲の保証ではなく、利用者が確認する広い探索起点です。追加しても検索条件には自動選択しません。保存済みの除外結果にも表示され、再度LLMへ問い合わせる必要はありません。確認済みの改訂注記（現在は `G05D1/02`）は旧版と変更版・WIPO資料リンクを示します。全ての旧版分類を収録する機能ではありません。

探索ラボのLLMは主に `english_terms` と `facets: [{id, terms, english_terms}]` を返します。提案語を探索計画へ追加し、英語検索案と分類辞書の語句照合に使います。「LLMの提案を、ここへ反映しました」で実際の追加語と反映先を表示し、重複による追加0件・未使用語・生成失敗を区別します。手入力の英語語句とLLMの提案語は併用します。期待したJSON項目がない応答を成功扱いにはしません。以前の版の計画には返答の内訳が保存されていないため、次回生成から反映記録が付きます。

再試行でも未完になる場合は、LM Studioなどの最大出力トークン数・停止文字列・コンテキスト長を確認してください。`finish_reason: stop` でもJSONが閉じていない場合があるため、終了理由だけでは成功扱いにしません。

## 学習方式

| 方式 | 学習するもの | 最低ラベル数 |
|---|---|---|
| 軽量学習 | 文字n-gram TF-IDF＋ロジスティック回帰 | 必要・不要 各2件 |
| Transformer | 事前学習モデル本体＋分類ヘッド | 必要・不要 各4件 |
| LLMにおまかせ | 調査基準と人の判定例を参考に、接続済みLLMが要否を判定 | 判定例なしでも基準・キーワードがあれば利用可能 |

特許の地図の学習欄で3方式を選べます。同じ欄に進捗バー、現在の工程、停止ボタンを表示します。LLM方式では今回の上限（1〜5,000件、初期値100件）と採用する信頼度を指定でき、処理済み・採用・保留件数を表示します。人の確定判定を優先し、未判定を先に、以前の保留を後に処理します。タイトル・要約・IPCと人の判定例を、設定したLocal LLMまたはAPIへ4件ずつ送ります。LLM方式は重みの学習を行わず、関連度と信頼度は別々の自己評価として保存します。低信頼・保留の回答を確定ラベルや高関連度予測に読み替えません。停止・失敗では完了したバッチの判定を保持します。

Local LLMによる地図の要否判定では、`response_format: json_schema` で判定の項目・件数・IDを指定します。この形式に対応するサーバーが必要です（[LM Studioの構造化出力](https://lmstudio.ai/docs/developer/openai-compat/structured-output)）。応答後もIDの重複・欠落や数値を検証し、不正なバッチは保存しません。同じ基準・モデル・接続種別で再開すると、前回の確定したLLM判定と関連度を保持します。

特許リストの行へマウスを重ねるかキーボードでフォーカスすると、公報ID・要約・出願人・IPC・判定理由が表示されます。Escで閉じられます。表示する本文は取り込まれた要約であり、未取得の公報全文ではありません。

「次の検索へ」では、公報のIPC欄とFI・Fタームからの対応候補を逆抽出し、必要・不要の判定と学習予測を別集計します。公式辞書にあるIPCだけを候補とし、ファミリー等の重複を考慮して必要側の支持が多いIPCを推奨します。由来と版の違いを表示し、対応候補を公報付与IPC欄に書き込みません。現在選択と推奨IPCが初期選択され、「推奨IPCで置き換える」で既存IPCを置き換えられます。予測だけのIPCは自動推奨せず、選ぶ前に根拠を確認できます。分類はOR条件で反映し、共有IPCをNOTにはしません。追加・解除と根拠公報を履歴に保存します。判断エージェントと統括モードも同じ分類抽出を使います。

Transformerを使う場合は追加依存を入れます。

```powershell
./.venv/Scripts/python.exe -m pip install -r requirements-transformer.txt
```

「接続・モデル」で、`AutoModelForSequenceClassification`対応のHugging Faceモデル名、またはローカルフォルダを指定してください。例として多言語BERT/DistilBERT系が適します。**tokenizerとsafetensors形式のモデル重みが必要です。** LLM用のGGUFファイルはこの学習機能には使用できません。

モデル未保存時のダウンロードは明示的に許可した場合だけ行います。初回の所要時間・メモリ量はモデルに依存します。モデル由来の任意コードは実行しません（`trust_remote_code=False`）。

CPU上でタイトル＋要約の先頭256トークン、バッチ4、3エポック、学習率2e-5で微調整します。後半の請求項や長い要約は学習対象外です。学習済みモデルを`data/models/<job-id>/`に保存します。初版では各回、設定したモデルから学習します。前回の重みから継続したい場合は保存先を次のモデルパスに指定します。

両クラス各4件以上でグループ分割可能な場合、人のラベルを独立評価用に取り分け、必要クラスの適合率・再現率・F1を表示。同一ファミリーIDは同じ側に置きます。ファミリーIDがない場合は同一タイトル＋要約を同じ側にします。少数標本の参考値で、特許集合全体の再現率ではありません。エージェント判定を含む学習では独立評価を表示しません。

関連度は未較正のモデルスコアです。人の判定を自動で書き換えるものではありません。ラベル変更時は以前の評価とスコアを無効化します。

## 判断エージェント

「判断エージェント」タブに調査基準を入力します。接続したLLMが候補から分類を選択、初案を作り、取り込み済みCSVの未判定特許を判定し、次の検索式を提案します。

- 1回の上限は1〜5,000件。判定理由・信頼度・人/エージェントの区別を保存。
- 地図・統括と同じLLM判定処理を利用します。判断エージェントと統括では保存済みの採用・不要・保留を再利用し、未判定だけを処理します。再評価する場合は地図で対象の判定を解除してください。地図のLLM実行では以前の保留も処理対象にできます。
- 人が確定した判定を優先し、低信頼度は保留。信頼度はLLMの自己申告値です。
- 「エージェントの判定も使って学習する」を選ぶと、判定後に指定方式で学習します。両クラスの必要件数が足りない場合は理由を表示して停止。
- 新しいNOT条件と、既知の必要特許を落とす追加条件を自動で採用しません。
- **外部の特許検索・CSVの自動ダウンロードは未接続**です。毎回「次のCSV待ち」で停止します。ログインやCAPTCHAを自動回避しません。
- 停止ボタンは処理の区切りで停止します。実行中のHTTPリクエスト（最大120秒）やモデル読み込みは完了を待ちます。

## 外部API / Local LLM

OpenAI互換の `POST {base_url}/chat/completions` を利用します。接続先のモデル名を指定し「保存して接続テスト」を押してください。

| 接続先 | Base URLの例 |
|---|---|
| Ollama | `http://localhost:11434/v1` |
| LM Studio | `http://localhost:1234/v1` |
| OpenAI互換API | 提供元が指定する`/v1`までのURL |

外部LLM使用時に送るものは、探索キーワード・分類候補・調査基準・判定対象特許のID/タイトル/要約/IPC/FI/Fタームです。APIキーとプロキシURLはメモリにだけ保持し、JSON書き出しやディスク保存には含めません。接続ホスト変更時は前のAPIキーを消去します。再起動時に再入力が必要です。

## プロキシ

LLM通信は「接続・モデル」のプロキシ欄で設定します。localhostを迂回する設定は既定で有効。CA証明書はPEMファイルのパスを指定できます。TLS証明書検証は無効化しません。

pipインストールやHugging Faceモデル取得には、起動するPowerShellで環境変数を設定します。下記はプレースホルダーです。

```powershell
$env:HTTPS_PROXY = 'http://proxy.example.com:8080'
$env:HTTP_PROXY = 'http://proxy.example.com:8080'
$env:NO_PROXY = 'localhost,127.0.0.1,::1'
```

社内CAが必要なモデル取得では`REQUESTS_CA_BUNDLE`、pipでは`PIP_CERT`などを組織の指示に合わせて設定してください。ブラウザーで開くJ-PlatPatはOS/ブラウザー側のプロキシ設定を使います。このアプリ自身は一般のWeb検索やスクレイピングを行いません。
